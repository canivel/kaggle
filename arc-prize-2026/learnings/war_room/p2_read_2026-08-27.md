## THE FINDING THAT ACTUALLY MATTERS — third paid confirmation of a memory we already had

P2 announced `attempt()` in `_PYTHON_TOOL_DESCRIPTION` — **a tool description.** Use rate **10.7 %**.

| **P2 retry seed 1** | **`_PYTHON_TOOL_DESCRIPTION`** | **certified, 24/25 games armed** | **10.7 %** | **25 %** |

`feedback_advertise_where_model_reads` **predicted this before the build**: *"an affordance advertised
only in a tool-call SCHEMA is not advertised."* We have now paid for that lesson **three times**, and
this is the cleanest instance — because unlike P1, **delivery here is not in doubt.** The trigger fired
on 24/25 games, the patch is certified, the boot check passed, and the model still declined the
affordance roughly 9 turns in 10.

Note too that **24 of 106 `attempt()` calls came on UNARMED turns**: the model knows the affordance
exists and occasionally reaches for it unprompted — so this is **not a discovery failure, it is a
preference failure.** Making the tool *more visible* is therefore the wrong repair.

**Consequence for the arm family.** Any future arm whose mechanism is "tell the model it may do X" must
carry a **pre-registered use-rate gate measured on retained artifacts BEFORE the build** — the way P2's
own D1 trigger-fireability was measured on 08-26 and correctly predicted 19/25 against the observed
24/25. *That half of the pre-work worked perfectly.* D1 was pre-measured and passed; D2 was not
pre-measurable and failed. **The asymmetry is the lesson: pre-measure the USE, not just the FIRE.**

## INSTRUMENT INCIDENTS — two, distinct, both new

**(1) `kaggle kernels output` can return exit 0 with a PARTIAL file set.** The first pull of this
artifact (08:23–08:25) returned **exit 0** and omitted **both** large logs — `arc3-p2-retry-eval.log`
(256,197 B) and `vllm-openai-server.log` (359,828 B). An identical re-pull minutes later retrieved both.

Scored against the partial pull, `p2_score.py` returned **`INFRA DEATH` / reason "served model absent"
/ `cert_facts: {}`** on a **completely healthy 2h13m run.** Had that verdict been taken at face value it
would have killed a certified arm on a download race. `feedback_audit_the_instrument` — and the empty
`cert_facts` was the tell: **an instrument reporting a sick subject while reporting zero facts about it
is describing itself, not the subject.**

→ **Fix required (not yet built):** a pull-completeness assertion — verify the kernel `.log` is present
and non-empty before any scorer runs, and re-pull if not. Also widen `certify()` beyond a top-level
`*.log` glob: the served model and vehicle were recoverable from `taaf_setup_env.json` and
`prompts/*.log`, both of which **did** download even in the partial pull.

**(2) P1's 0-byte kernel log is REAL and is a DIFFERENT defect.** Tested today on a **third**
independent pull: `arc3-p1-notes-eval.log` came down at **0 bytes** while `vllm-openai-server.log`
(358,981 B) and `stdout.log` (40,576 B) arrived intact **in the same pull**. So the 08-23 finding
**stands and is re-confirmed** — it is not the partial-pull race. Two distinct failure modes; today
separated them. (P1 remains sealed DELIVERY FAILURE ⇒ re-scope-never-re-read, so this changes nothing
operationally — but a P1 *rebuild* still needs the log-capture fix first.)
