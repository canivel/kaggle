## PRIORITY — Qwen2.5-VL tool-call format adherence on vLLM (A17 canary) [line 5]

**Diagnosis confirmed as a known, reproducible failure class, not a one-off.** The canary symptom —
Qwen2.5-VL-72B-AWQ on vLLM `--tool-call-parser hermes` emitting markdown-fenced ```python``` / ```json```
blocks instead of `<tool_call>` markup on 1200/1200 in-game turns despite a correct short-probe tool call —
matches the documented Qwen-family behavior almost exactly. Root cause is **not** the long system prompt or
38-message history per se; it is that **Qwen2.5 chat templates do not reliably steer the model into hermes
`<tool_call>` markup, and the VL variants' default templates ship with broken/absent tool-call support.**
`hermes` prompting is *ignored* by the model; measured on Qwen2.5-Coder the split is **60% fenced code + 40%
plain JSON, ~0% hermes tags** with no format instruction → 100% fenced. Under `tool_choice="auto"` (our canary
mode), vLLM extracts tool calls **from raw text** and silently fails when the text is a fenced block →
`finish_reason: stop`, empty `tool_calls`. Long/verbose system prompts add a *second, milder* degradation
(direct-answer instead of tool-call) on smaller models but do **not** flip the format channel — so our long
prompt + history is an aggravator, not the primary cause. Concrete, cited mitigation ladder (strongest first):

1. **`tool_choice="required"` + structured-outputs (xgrammar) — ADOPT (canary re-run).** vLLM docs (stable):
   `required` "guarantees at least one tool call **using structured outputs … regardless of the `strict`
   field**" — i.e. schema-constrained (FSM/xgrammar) decoding that **forces** valid tool-call JSON conforming
   to the function schema, bypassing the fenced-code channel entirely. This is model-format-agnostic and does
   not depend on the model choosing hermes tags. **Reason: directly neutralizes the 1200/1200 fenced-block
   failure with no prompt surgery; single flag on the canary re-run.** Caveats to pre-register: (a) known
   "Failed to advance FSM" errors with `required` at low temperature / complex schemas — keep our
   `set_data`/action schema minimal and temp > 0; (b) "schema contains features not supported by xgrammar"
   for exotic JSON schemas — validate the ACTION6 tool schema against xgrammar before the screen; (c) docs
   advise **restating the expected schema in the prompt** so the model's intended generation aligns with the
   forced grammar (cheap, do it).
   [tool_calling docs](https://docs.vllm.ai/en/stable/features/tool_calling/) ·
   [required/xgrammar reliability](https://github.com/vllm-project/vllm/issues/16321) ·
   [FSM-advance failure](https://github.com/MoonshotAI/Kimi-K2/issues/41)

2. **Custom `<tools>`-tag tool parser + few-shot chat template — ADAPT (low), prompt-side, no build.** The
   `hanXen/vllm-qwen2.5-coder-tool-parser` plugin replaces hermes with a `<tools>`-tag parser and injects
   few-shot `<tools>` examples via the chat template: measured **100% format compliance** (50/50 on 7B & 32B,
   48/50 on 14B — the two misses were model JSON malformation, not parser). Crucially it also **tested a
   ~90-line verbose system prompt** and held **45/46–50/50** format compliance — direct evidence that a
   few-shot-anchored template survives our long-prompt regime where bare hermes collapses. **Reason: a
   deterministic fallback if `required`/xgrammar hits an FSM/schema snag on the VL schema; the few-shot
   anchoring is the transferable idea even without the plugin — inject 1–2 in-context tool-call exemplars
   into the canary system prompt.** Off-the-shelf plugin is Coder-specific; for VL we'd port the `<tools>`
   template idea, not the binary. Design-only, no cloud spend.
   [plugin + compliance stats](https://github.com/hanXen/vllm-qwen2.5-coder-tool-parser) ·
   [dedicated-parser feature req](https://github.com/vllm-project/vllm/issues/32926)

3. **Confounder to rule out on the canary — streaming.** vLLM `--tool-call-parser hermes` has an open bug
   (#31871, repro'd on **0.13.0**) where **streaming mode returns raw `<tool_call>` text in `content` with
   `finish_reason: stop` and no parsed `tool_calls`**, while non-streaming parses fine. If the canary harness
   streams, part of the "no tool call" signal could be this parser bug, not pure model misformat. **Action:
   re-run canary non-streaming (or verify stream path) before attributing 100% to the model.** Note our
   symptom was *fenced python*, not raw `<tool_call>` tags, so this is a secondary confounder, not the primary
   cause — but cheap to exclude.
   [streaming hermes raw-text bug](https://github.com/vllm-project/vllm/issues/31871)

4. **Template-regression watch — verify the served VL template actually has tool support.** Qwen2.5-VL AWQ
   repos have a history of a `tokenizer_config.json` chat-template commit **removing** tool-calling
   (Qwen2.5-VL-32B-AWQ disc #10: `tool_choice='auto'` broke; `--tokenizer-revision` rollback later stopped
   working; manual template restore hung vLLM). **Action: before the A17 screen, dump the exact chat template
   the served 72B-AWQ build resolves and confirm it contains the `<tool_call>` / tools block — a silently
   tool-stripped template alone reproduces our symptom.**
   [Qwen2.5-VL-32B-AWQ template-broke-tools](https://huggingface.co/Qwen/Qwen2.5-VL-32B-Instruct-AWQ/discussions/10) ·
   [Qwen2.5-VL 7B/72B tool-call issue #1093](https://github.com/QwenLM/Qwen3-VL/issues/1093)

**Deliverable summary:** the canary failure is a textbook Qwen tool-format problem. **Primary fix =
`tool_choice="required"` (xgrammar-forced tool JSON), secondary = `<tools>` few-shot chat template, plus two
cheap confounder checks (non-streaming; verify template has tool support).** All are free (flag/prompt/config,
no cloud spend) and settle at the A17 screen build.

## Vision-language ARC — new-to-set, VL-bet-relevant [line 5 context]

**Think Visually, Reason Textually: Vision-Language Synergy in ARC**
([arXiv:2511.15703](https://arxiv.org/abs/2511.15703), Nov 19 2025 rev Nov 26 — **out of window**, new-to-set)
— finds **"naively rendering ARC grids as images degrades performance due to imprecise rule execution"**;
proposes VLSR (modality-aligned subtasks: vision for global pattern abstraction, text for precise rule
execution) + Modality-Switch Self-Correction (vision verifies text reasoning). ARC-AGI-1/2 style, not
explicitly ARC-AGI-3. **Verdict: PARK (VL-bet context).** **Reason:** it is the cleanest external caution
that the A17 multimodal 72B-VL bet must **not** assume "just feed the grid as an image" wins — on grids,
image rendering can *hurt* precise execution; the value of vision is global-pattern/verification, with text
carrying exact cell-level rules. This does not change the bet (the harness is multimodal and the wall-closer
must be a VL model to consume game frames) but it **shapes how we should present grids**: keep a precise
textual grid encoding alongside frames rather than relying on rendered images for rule execution. Hold as a
design note for the VL prompt-format; no build. (Out-of-window, so logged as reference, not an in-window find.)
