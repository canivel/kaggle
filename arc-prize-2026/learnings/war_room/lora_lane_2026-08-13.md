## 0. Why this lane and not another one

Every runner-side mechanism we have tried died the same way. INFORM was refuted twice (P1 mech-C
96.3% delivery, EFFNOTE 93.8% — both inside the control spread). CONSTRAIN was refuted (P2's cap
deletes level-completions; 79–85% of batches are single actions; the agent persists **deliberately**
across informed observations). The harness diff (`harness_diff_2026-08-13.md`) then closed the last
door: **our shipped kernel is byte-identical to the 1.62**, and our per-draw distribution is
statistically indistinguishable from the field's (ours n=29, 0.9503/0.1513; field k≤1 s≥0.60 n=85,
0.923/0.159). There is nothing left to copy and nothing left to tell the model.

What is left is the weights. That is also where the public frontier moved: `auxentr` (#163, 1.25)
shipped `iseesmth/arc3-nca-qwen36-sft` + `duck-harness-nca-qwen36-adapter-20260811` on 08-11/12 — a
LoRA adapter on the duck's own Qwen3.6-27B. [V]

### 1.3 Does it train on ONE 96 GiB card? — YES, and the loss is what decides it

Envelope: RTX PRO 6000 Blackwell, **~95.6 GiB usable**, SM120, single GPU, no internet.
Per-token, batch 1, gradient checkpointing, frozen base: stored layer inputs `64 × 5120 × 2 B` =
**0.655 MB/token**; **logits `248,320 × 2 B` = 0.497 MB/token**, ×3 with the fp32 CE upcast and its
gradient. [C]

| line item | S = 8,192 | S = 16,384 | S = 32,768 |
|---|---:|---:|---:|
| BF16 frozen base (27.35 B × 2 B) | 54.7 GB | 54.7 GB | 54.7 GB |
| stored activations | 5.4 GB | 10.7 GB | 21.5 GB |
| recompute peak + workspace | ~2.0 GB | ~2.0 GB | ~2.0 GB |
| adapter + fp32 master + Adam + grads, **B/r32** | 2.3 GB | 2.3 GB | 2.3 GB |
| **naive** cross-entropy | **12.2 GB** | **24.4 GB** | **48.8 GB** |
| checkpoint-chunked CE, chunk 256 — **measured, S-independent** | **0.8 GB** | **0.8 GB** | **0.8 GB** |
| **total, naive CE** | 76.6 GB | **94.1 GB — 1.5 GB of headroom** | **129.3 GB ✗** |
| **total, chunked CE** | **65.2 GB** | **70.5 GB** | **81.3 GB ✓** |

**It fits, and the thing that decides whether it fits is the loss, not the model.** With a 248 k
vocab, naive cross-entropy at 32 k is 48.8 GB by itself and blows the card; at 16 k it survives on
1.5 GB of headroom, which is not a margin anyone should ship. **Chunked cross-entropy is mandatory.**

**The CE row above is now measured, not guessed — and the first version of it was wrong in
mechanism.** Stage 1c (§5.5) on the local 3080 found that a plain Python loop over chunks gives only
a **2.3×** reduction, because autograd keeps every chunk's logits alive until backward runs. The
saving only materializes if each chunk is **checkpointed** so its logits are dropped and recomputed
in the backward pass. Measured at vocab 32 000: naive 1,500 MiB → plain loop 642 MiB (2.3×) →
**checkpointed 110 MiB (13.7×)**, and with `lm_head` frozen (our configuration — it is in the quant
recipe's ignore list and is not a LoRA target) the peak tracks
**≈ 3.2 × chunk × vocab × 4 B and is independent of sequence length**. At 27B scale that is
**0.8 GB at chunk 256**, flat from 8 k to 32 k.

The totals barely moved (82.9 → 81.3 GB at 32 k) but the reasoning did: the earlier "÷20" was a
guess that happened to land near the right absolute number for the wrong reason, and the
implementation it implied — a plain chunk loop — would have OOMed at 32 k. `recompute=True` in
`train_kernels.chunked_cross_entropy` is load-bearing, and it is defaulted on.

Adapter and optimizer state are a rounding error at every rank — **rank is free, sequence length is not.**

### 1.4 The training environment — the pinned duck wheelhouse CANNOT train this model

This is the finding that reshapes stage 2, and it cost nothing: two file listings and one config
field, all read locally. [V]

| | duck pinned `driessmit1/arc3-vllm-h100-wheelhouse-v3` | `jcole75/arc3-qwen36-runtime-wheels` |
|---|---|---|
| **transformers** | **4.57.6 ✗** | **5.13.0 ✓** |
| torch | 2.10.0 | 2.11.0+cu129 |
| compressed-tensors | 0.14.0.1 | 0.17.0 |
| safetensors | 0.7.0 | 0.8.0 |
| vLLM | **0.19.0** | 0.24.0 |
| **peft** | **absent** | **absent** |
| **accelerate** | **absent** | **absent** |
| **liger-kernel / cut-cross-entropy** | **absent** | **absent** |

**The checkpoint declares `transformers_version: 5.6.2`, and `qwen3_5` /
`Qwen3_5ForConditionalGeneration` does not exist in transformers 4.57.6.** HF-based training inside
the duck's own pinned wheelhouse is therefore **blocked at the transformers version, before FP8
decompression is even reached.** The training environment must be jcole75's wheelhouse (5.13.0 ≥ 5.6.2).

That does not contradict §2's "do not adopt jcole75 for serving". **Training and serving run in
different wheelhouses on purpose:** training is an offline build whose only output is a 20–300 MiB
file, so its runtime never touches a scored run, while serving stays byte-identical to the 1.62
config. The adapter is a portable artifact; the environment that produced it is not part of the
submission.

Three further consequences, each of which would otherwise have been a silent stage-2 failure:

- **No `peft`.** LoRA must be hand-rolled for training (~20 lines: `y += (x @ Aᵀ) @ Bᵀ · scale`) and
  the adapter files written directly with `safetensors`. That is fine — vLLM parses
  `adapter_config.json` itself and never imports peft — and the key convention is now known from
  ground truth:
  `base_model.model.model.language_model.layers.{i}.self_attn.{q,k,v,o}_proj.lora_{A,B}.weight`, F32.
- **No `accelerate`.** `device_map=` / `low_cpu_mem_usage=` are unavailable, so a 54.7 GB
  CPU-then-`.cuda()` load is not on the table. The loader must be meta-device init plus a streaming
  per-tensor assign straight to GPU, dequantizing FP8 inline — which for per-tensor static FP8 is one
  line: `w.to(bfloat16) * weight_scale`.
- **No fused CE.** Chunked CE — mandatory per §1.3 — must be hand-written (~30 lines).

### 1.5 Is FP8-base training blocked? — Yes directly, no in practice

PEFT/bitsandbytes support NF4 and int8 frozen bases; they do **not** train a LoRA against a live
compressed-tensors FP8 base. [INF] We do not need them to:

- **B1 (recommended): decompress at load.** Materialize BF16 from the FP8 file we already attach
  (`run_compressed=False`, or the streaming loader §1.4 forces on us anyway). Freeze, attach LoRA,
  train. **The adapter is then trained against exactly the weights it is served against** — strictly
  better than auxentr, who trained on `unsloth/Qwen3.6-27B` (BF16) and serves on the FP8 snapshot, a
  silent base mismatch. Cost: 54.7 GB resident. **[UNVERIFIED — gate G-T1.]**
- **B2 (fallback): BF16 base as a separate dataset.** ~55 GB we do not have locally and cannot buy;
  reintroduces the mismatch. Do not lead with this.
- **B3 (fallback): QLoRA NF4.** ~13.7 GB base, huge headroom — but bitsandbytes is in **neither**
  wheelhouse, so it needs a wheel we would have to source, and it stacks quantization error on a base
  that is already FP8 at serve time.
- **B4: train a smaller sibling and test transfer.** Only as a pipeline smoke; the 3080 covers that
  for free (§1.6).

### 1.5b Hours per epoch — against real prompt lengths

**The brief's assumption that our prompts are 4–8 k is roughly half the truth.** Measured on the
stage-1 corpus, over the real harness prompt with history and image parts: **mean 8,142, median
7,083, max 22,541 tokens** per turn-example (chars/3.5). [V] The harness's context budget is 32,768,
so 32 k is the true ceiling and the table above must hold there.

FLOPs/token ≈ `6 × N_matmul` with checkpointing on a frozen base, `N_matmul ≈ 24.8 B` →
**1.49e11 FLOP/token**. [C] Blackwell RTX PRO 6000 dense BF16 ≈ 503 TFLOPS peak; at a realistic
20–30% MFU for a checkpointed LoRA run → 100–150 TFLOPS → **670–1,010 tok/s**; use **820**. [INF]

**Measured packing ratio on the real corpus: 3.7×.** 127 turn-examples = **1.034 M** tokens unpacked;
the same 33 conversations packed one-per-game = **0.279 M** tokens (mean 8.5 k, max 22.5 k per game —
inside the 32 k ceiling). [V]

| dataset shape | tokens | hours/epoch @ 820 tok/s |
|---|---:|---:|
| **this corpus, 127 turns, unpacked** | 1.03 M | **0.35 h** |
| **this corpus, 33 conversations, packed** | 0.28 M | **0.09 h** |
| 2,000 turn-examples, unpacked | 16.3 M | 5.5 h |
| 2,000 turns packed (~520 games, at 3.7×) | 4.4 M | **1.5 h** |
| 8,000 turns packed (~2,100 games) | 17.6 M | 6.0 h |

**Design consequence: pack per conversation.** Turn *t* is turn *t−1* plus one exchange, so training
turns as separate rows pays for the same prefix 3.7× over — and almost all of that compute is spent
on tokens carrying **no loss** (targets are ~200 tokens against an ~8 k prompt). One sequence per game
with the loss mask on **every** assistant turn is the difference between 5.5 h and 1.5 h per epoch at
realistic corpus size.

**Against the 30 GPU-h/week free allowance:** a 3-epoch packed run on ~500 games is **~4.5 h**, well
inside one Kaggle kernel and **~15% of the weekly budget**, leaving room for the smokes, an
eval-in-kernel and a rebuild. **It fits, with margin.** The binding constraint is Kaggle's 12 h
per-kernel wall clock, not the weekly hours — and at 820 tok/s that wall clock buys ~35 M tokens,
i.e. ~15,000 packed turns, far more data than the searcher can currently produce.

### 1.6 The local 3080 — usable, for exactly one thing

10 GB. It cannot hold the 27B in any precision (13.2 GB even at NF4). It **can and should** run the
whole pipeline against a small Qwen3 sibling (0.6B/1.7B): chat-template rendering, loss-mask
correctness, packing, PEFT wiring, one real optimizer step, one adapter save/load. That is precisely
the `feedback_test_before_submit` class of failure (v38 scored 0.00 on a missing import) and it costs
nothing. **Yes — smoke on the 3080, never train on it.**

### 3.3 What the adapter is taught (policy, never answers)

Rendered assistant turns encode four behaviours and nothing else:

- **P1 commit.** A verified sequence goes out as ONE batched `action([...])`. This attacks the 79–85%
  single-action-batch finding directly, from the weights instead of the prompt.
- **P2 do not re-probe settled state.** Every turn after the first is a commit; the note explicitly
  names the question the last batch already answered and declines to re-ask it. This is the exact
  behaviour INFORM and CONSTRAIN both failed to move from outside.
- **P3 quadratic cost.** The note states the scoring rule in its own terms and the running
  actions-used against the level's human baseline.
- **P4 derive, don't memorize.** MOUSE targets are emitted as an **index into the segmentation the
  model can see** — `_center(nodes[k])` after `sorted(seg['nodes'], key=pixels)` — whenever the
  coordinate is recoverable that way, instead of a literal `row=34, col=57`. The datasheet reports
  `derived_click_fraction`; literals are counted, not hidden.

Legality: no game id is read anywhere in the generator; the candidate set comes only from
`available_actions` and the board's own segmentation.

### 3.4 The holdout protocol (how we find out it is fake)

Three gates, each strictly harder than the last, each reading a *different* population:

- **H1 — DEV transfer (CPU, free, before any GPU).** 36 unseen non-public families. Measure the
  adapter's actions-per-cleared-level against the *same* base model on the *same* families.
  No improvement on unseen families ⇒ the adapter memorized ⇒ **kill**.
- **H2 — EVAL, in-kernel, adapter vs base, same seed, same everything.** The 25 scored games.
  Primary endpoint **M0 = median actions per cleared level, per game**, read against the three
  block-free control runs, **control-side statistic computed first** (the Mechanism-C regression-to-
  the-mean trap). Secondary: RHAE via `duck_eval/warpack/*_score.py`.
  Non-harm gate: `levels_completed` ≥ min of the controls. Any trade of levels for efficiency kills it.
- **H3 — the discriminator.** Report H1 and H2 **side by side**. A lane that improves on EVAL but not
  on DEV is memorization wearing a rosette, and the private set has more games. Under
  `feedback_arc_generalization_first`, H1 < H2 by a wide margin is a **kill**, not a win.

### 4.3 Two defects found and fixed while building this

1. **The searcher's voice leaked into the note.** The first render said *"the sequence my search
   verified for this state"* — something the student can never truthfully say. Training on it teaches
   the model to **claim verification it does not have**. Rephrased to *"the shortest sequence
   consistent with the evidence so far"*, applied to targets **and** to assistant turns already baked
   into history (`rewrite_notes.py`, 556 phrasings across 127 examples).
2. **Multi-click batches can only index the pre-batch board.** For a batch with several MOUSE actions,
   only the first click's segmentation index is guaranteed valid. The harness-replay verification is
   the safety net — a plan whose rendered code diverges clears fewer levels and is dropped. Zero
   divergences in this corpus, but the net is doing real work and must stay.

### 4.4 Honest gaps in the stage-1 corpus

- **127 examples, not 500.** The binding constraint is the **searcher**, not the pipeline: 88 of 129

- **The corpus is short-trajectory-biased.** Mean 3.85 turns/game. Games whose *level 1* is hard are

### 5.3 The CUDA-13 loader trap — inherited from the 122B lane, before it cost us an hour

`brain-122b`'s boot canary v1 ERRORed after ~1 h without ever loading a weight: [V, their run]

```
vllm/platforms/cuda.py:22  import vllm._C_stable_libtorch
ImportError: libcudart.so.13: cannot open shared object file
```

**vLLM 0.24.0 links CUDA 13; the Kaggle image ships CUDA 12.** The CUDA-13 runtime therefore exists
only as pip wheels that `pip install --target` drops under `<SITE_PACKAGES>/nvidia/*/lib` — a path
the dynamic loader has never heard of. The duck's `vllm_env()` sets `PYTHONPATH` **and nothing
else**, which was always correct for its own CUDA-12.8 build because the *image* supplied those
`.so` files.

**Stage S is unaffected** — it stays on the duck's pinned 0.19.0 wheelhouse, CUDA 12.8, image-provided,
`vllm_env()` unchanged. That is the correct configuration and it must not be touched. [V]

**Stage T is directly exposed.** §1.4 moves training to jcole75's wheelhouse precisely because it
carries transformers 5.13.0 — and that is the same wheelhouse that just killed a kernel. Two
mitigations, both cheap, both mandatory before stage T is pushed:

1. **Take the fix, do not rediscover it.** `duck_eval/a17/build_b122_boot_canary.py` now has
   `_b122_cuda_lib_dirs()` (globs `nvidia/*/lib`, `nvidia/*/lib64`, `torch/lib`, `cusparselt/lib`
   under the install target) feeding `LD_LIBRARY_PATH` — **appending, never clobbering** — plus
   `_b122_assert_cuda_runtime()`, which runs *after* the install and *before* the weight load and
   names the v1 error. Port both verbatim; do not re-derive them.
2. **Install a minimal subset.** Stage T needs `transformers`, `torch`, `safetensors`, `numpy` — it
   does **not** need vLLM at all, and vLLM is what links `libcudart.so.13`. Installing the runtime
   requirements file wholesale imports the failure for no benefit. Note this does not remove the
   trap: `torch-2.11.0+cu129` still ships its CUDA runtime as `nvidia/*` wheels under the target, so
   mitigation 1 stands on its own.

The general lesson, which is worth more than the specific fix: **a wheelhouse swap is not a version
bump, it is a change of the native-library contract with the image.** Any lane that changes wheels
pays this hour once. We have now paid it once, in someone else's lane.

### 5.5 Stage 1c — the hand-rolled numerics, validated on the 3080

Neither wheelhouse ships `peft`, `accelerate` or a fused CE (§1.4), so LoRA, the loader and the loss
are all ours. A wrong constant in any of them would not crash — it would train, produce a plausible
adapter, and read as "LoRA didn't help" after four GPU-hours. The 3080 cannot rehearse the run, but
it can prove the arithmetic, and every check has a reference implementation on the other side of it.

`duck_eval/lora/train_kernels.py` (production, embedded verbatim into stage T) +
`duck_eval/lora/test_train_kernels.py` (validation). **30 checks, 0 failing**, on
torch 2.6.0+cu124 / RTX 3080. [V]

| test | what it proves |
|---|---|
| T1/T2 | LoRA forward == explicit merged-weight reference (2e-5); **rsLoRA scale is α/√r = 8.0, not α/r = 2.0** — a silent 4× error vLLM would faithfully reproduce at serve time; a `B=0` adapter is an **exact** no-op, which is what makes the `noop` serve probe valid |
| T3 | `attach_lora` hits exactly the intended modules and nothing else; trainable count is exactly `r·Σ(in+out)`; base, embeddings and `lm_head` all frozen |
| T4 | chunked CE matches `F.cross_entropy` in **value and both gradients** (<1e-6) including `ignore_index`; an all-masked batch returns 0, not NaN |
| T5 | **the bug this stage existed to find** — see below |
| T6 | FP8 per-tensor dequant reconstructs to FP8 precision and returns bf16 |
| T7 | meta-init + `stream_assign` reproduces a normally-loaded model's outputs exactly (no `accelerate`, no host-RAM spike) |
| T8 | adapter save → re-read is bit-exact, in the ground-truth PEFT key convention |
| T9 | one optimizer step: gradients reach the adapter, loss falls over 10 steps, **frozen base weights bit-identical afterwards**, prompt tokens excluded by the mask |

**T5 found a real defect in my own design, which is the whole point of doing this locally.** My first
`chunked_cross_entropy` was a plain Python loop over sequence chunks. It is numerically correct —
T4 passes on it — and it delivers almost none of the promised memory saving, because **autograd
retains every chunk's logits until backward runs**. Measured, vocab 32 000, 4 096 tokens:

| variant | peak | vs naive |
|---|---:|---:|
| naive `F.cross_entropy(F.linear(...))` | 1,500 MiB | 1.0× |
| plain chunk loop | 642 MiB | **2.3×** |
| checkpointed chunks, trainable `lm_head` | 204 MiB | 7.4× |
| **checkpointed chunks, frozen `lm_head` (our config)** | **110 MiB** | **13.7×** |

Chunk sweep with the head frozen shows peak tracking **≈ 3.2 × chunk × vocab × 4 B and flat in
sequence length** (chunk 128 → 63 MiB, 256 → 110, 1024 → 391, 4096 → 1508). At 27B scale that is
**0.8 GB at chunk 256, from 8 k to 32 k**, which is what §1.3 now uses.

The conclusion did not change — 32 k still fits — but **the mechanism I had written down was wrong,
and the implementation it implied would have OOMed at 32 k on the real card.** That is one GPU-hour
and one confusing failure avoided for free. `recompute=True` is the default and is load-bearing.

## 7. R-7 — is this corpus teaching MORE-solved or FASTER-solved? Measured answer: **faster-solved only.**

The coordinator asked for this judgement now rather than at stage 3. It is not a judgement call — it
is measurable from the corpus, and the measurement is unambiguous and unflattering.

### 7.1 The corpus is drawn from the easy tail, and the gap is 2.75×

Level-1 human action baseline, for the families that produced a usable plan versus the families the
searcher could not crack: [V, read from each environment's own `metadata.json` via `base_actions_per_level`]

| group | n | L1 baseline: min / p25 / **median** / p75 / max | mean | median levels |
|---|---:|---|---:|---:|
| **in the corpus** (`ok`) | 33 | 1 / 3 / **4** / 10 / 111 | 11.7 | 5 |
| **missing** (`no_plan`) | 87 | 2 / 6 / **11** / 26 / 1299 | 32.8 | 6 |
| dropped on efficiency | 8 | — / — / **8** / — / — | 8.9 | 6 |

**The median missing game needs 2.75× more human actions on level 1 than the median corpus game, and
85.1% of missing games sit above the corpus median.** The searcher did not sample the family pool —
it sampled the easy end of it. Every example the adapter will see comes from a game that was already
solvable in a handful of actions.

### 7.2 The corpus contains zero examples of the behaviour it is supposed to teach

Worse, and this one is a design defect rather than a sampling artefact. Counting every tool result in
the corpus: [V]

| | count |
|---|---:|
| tool results | 334 |
| `board_changed: True` | **334** |
| **`board_changed: False`** | **0** |
| `game_over: True` | **0** |
| examples whose history contains any no-op | **0 of 127** |

**P2 — "stop re-probing settled state" — has no positive examples in the corpus.** The model never
sees an action that did nothing, and therefore never sees the behaviour of *observing* a dead end and
*not* repeating it. Nor does it see a single failure or recovery.

The cause is my own pruning. Greedy search emitted 1,327 actions; leave-one-out kept 589 and
**deleted 738 — and those 738 deletions are precisely the exploration.** The pruning that makes each
trajectory efficient also removes every trace of how the efficiency was discovered. What survives
teaches the model to be *confident*, not to be *correct* — and at inference it cannot be confident,
because it has never seen the board before.

### 7.3 The honest verdict

**This corpus teaches faster-solved. It cannot teach more-solved, by construction:**

1. Every example comes from a trajectory that already cleared a level. The 88 families where level 1
   was never cracked — the population where the score is actually lost — contribute **nothing**.
2. The efficiency floor (`min_ratio 0.60`) *actively removes* the least efficient survivors, which
   are the ones nearest the capability limit. The filter is biased against exactly the hard cases.
3. All four encoded behaviours (P1 commit, P2 don't re-probe, P3 quadratic cost, P4 derive) are
   **efficiency** behaviours. Not one is a capability behaviour.

So R-7 is not mitigated by this corpus — **it is instantiated by it.** Our own 08-12 refutation caps
pure efficiency at ≈1.26–1.36 LB, short of the 1.64 prize line, and this corpus is a pure-efficiency
instrument. Trained as-is and working perfectly, it buys the efficiency ceiling and no more.

**And my strategic inference from that was wrong — corrected, with the correction verified.**
I wrote that efficiency-only "buys the efficiency ceiling and no more", i.e. stops short of gold. The
coordinator caught the error: **1.26–1.36 is a per-draw MEAN** (it was computed by re-scoring our own
runs at human action counts), and **gold is judged on best-of-k**. Means compound with draw count.

Re-derived independently with Blom order statistics, `E[max] ≈ μ + σ·Φ⁻¹((k−0.375)/(k+0.25))`, σ =
0.151, ~80 draws left to Nov 2 — reproduces their table exactly: [C]

| per-draw mean | E[max@29] | **E[max@80]** | E[max@110] |
|---|---:|---:|---:|
| 0.950 (today) | 1.256 | **1.316** | 1.333 |
| **1.26** (efficiency floor) | 1.566 | **1.625** | 1.642 |
| **1.36** (efficiency ceiling) | 1.666 | **1.725** | 1.742 |

Gold **1.58**, prize line **1.64**. **Efficiency-only clears gold with margin, and the floor case
essentially reaches the prize line.** The mechanism analysis in §7.3 stands; the strategic conclusion
drawn from it did not. This lane is not a consolation prize.

**Two caveats on the correction, both mine, neither fatal:**

1. **The calibration claim compares mismatched k.** "Predicts 1.316, observed best-of-29 is 1.33"
   matches an **80**-draw expectation to a **29**-draw observation. The like-for-like number is
   **E[max@29] = 1.256 vs 1.33 observed** — the model *under*-predicts by 0.074. That is conservative,
   not wrong, and right-skew in the draw distribution makes Blom-normal under-estimate the max anyway.
   But it is not the tight calibration the coincidence suggests.
2. **The conclusion is sensitive to σ, and efficiency plausibly shrinks σ.** Much of our dispersion
   *is* waste variance; removing waste removes it. At the floor case μ = 1.26: [C]

   | σ | E[max@80] @ μ=1.26 | @ μ=1.36 |
   |---:|---:|---:|
   | 0.151 (today) | 1.625 ✓ | 1.725 ✓ |
   | 0.120 | **1.550 ✗** | 1.650 ✓ |
   | 0.100 | **1.502 ✗** | 1.602 ✓ |
   | 0.060 | 1.405 ✗ | 1.505 ✗ |

   **An adapter that reaches μ=1.26 while halving σ misses gold.** The bet needs the mean to rise
   *without* the spread collapsing; only the ceiling case tolerates σ falling to ~0.12.
   **Consequence: H2 must report σ as well as μ.** A "successful" arm that tightens the distribution
   can be worth less than a noisier one with the same mean — which is counter-intuitive enough that
   it needs to be pre-registered rather than discovered.

### 7.4 What would make it teach more-solved — ranked, with the cheap one first

1. **Stop deleting the informative failures — BUILT AND VALIDATED TODAY (§7.5).** `--noops-per-level`
   re-inserts genuine dead actions as isolated probe turns. Verified on 5 families: **19
   `board_changed: False` events where v0 had 0**, at a measured cost of ~0.15 on the efficiency
   ratio. Default for the next full generation; not yet applied corpus-wide.
2. **Keep game-over and recovery segments (cheap).** Currently zero. A trajectory that died and
   restarted teaches recovery; pruning deletes it as "reset-undone".
3. **Raise searcher strength, not just depth (running).** The `v1hard` pass re-attacks the 96 failed
   families at 6 seeds with a relaxed floor. Every family it converts moves the corpus median toward
   the pool median. This is the only lever here that adds genuinely harder games.
4. **On-policy STaR against unsolved levels (stage 3, the real fix).** Sample the *actual* Qwen on the
   families the searcher cannot crack, keep the trajectories that clear a level at any cost, and
   train on those. That is the only source in the ranking that can teach a capability the searcher
   does not already have — a searcher can never demonstrate what a searcher cannot do.

Items 1–2 are corpus-design changes and belong in stage 1b. Item 4 is the one that actually answers
R-7, and it needs a served model, so it is gated behind stage S and stage T.

### 7.5 Fix #1, built and validated: the corpus can now contain "that did nothing"

Two attempts, and the first one silently did nothing — worth recording because both failure modes are
non-obvious.

**Attempt 1: replay the raw trace and re-insert its no-ops.** Found almost none. The greedy searcher
evaluates candidates on *clones* and only commits the winner, so it essentially never commits an
action it has just watched do nothing. The 738 pruned actions were mostly *reversible detours* — they
moved the board, they just weren't needed — not dead ends.

**The dead ends live in the rejected set, not the committed trace.** `greedy_search` now records
every candidate whose 1-ply lookahead proved it leaves the grid hash and level unchanged:
`Plan.noop_candidates`, capped at 64. The searcher gets these free by cloning; a real agent pays one
action each, which is exactly the cost the demonstrated policy should be seen paying.

**Attempt 2: inject them into the plan.** Action counts rose, and the corpus still contained **zero**
`board_changed: False`. Cause: `solver.step_env` aggregates `board_changed` with `any()` across a
batch, so a no-op mixed in with real actions reports `True`. **A no-op only teaches anything if it is
alone in its turn.** Injected actions are now tagged `_probe` and `split_into_turns` gives each one
its own turn (`_to_input` reads only `id`/`x`/`y`, so the tag is inert everywhere else).

Verified on 5 families at `--noops-per-level 1`: [V]

| | v0 | with probes |
|---|---:|---:|
| tool results | 24 | 38 |
| **`board_changed: False`** | **0** | **19** |
| examples whose history contains a no-op | 0 / 17 | **14 / 20** |
| efficiency ratio (median of the 5) | 1.00 | 0.82 |

The rendered pair reads as intended — a probe turn that spends one action to settle a question,
followed by a commit turn that names it as settled:

> *World model: level 1, I do not yet know whether MOUSE does anything from this state.*
> *Plan: spend exactly one action to settle it. One probe is cheap; re-asking the same question every
> turn is what makes a run expensive under (human/mine)^2.*

> *World model: level 1, MOUSE changed nothing from that state. That question is settled, so it is off
> the table and I will not spend another action re-testing it.*

**The trade is real and is stated as a trade:** ~0.15 of efficiency ratio per level buys the only
positive examples P2 can have. Given that P2 is the behaviour INFORM and CONSTRAIN both failed to move
from outside, and that a corpus which cannot demonstrate it is not going to teach it from the weights
either, the trade looks right — but it is a judgement, and it is now a measured one that a later run
can revisit by turning the flag down.

### 7.6 The probe fix was half wrong — and checking it found a bigger defect

`brain-122b` pushed back on §7.5 with evidence from the P2 refusal
(`learnings/war_room/p2_prereg_2026-08-13.md`), and the pushback was worth more than the fix:

- In **all four** recorded instances, the level-completing action was the **last action of a long
  stall-gated batch**: tu93 L1 (16, completion at 16), ar25 L1 (15, at 15), sp80 L1 (4, at 4),
  sp80/effnote (6, at 6). **ar25 and tu93 need N ≥ 15.**
- P2's batch cap **deleted 5 level completions**, and every lc-cutting rule came out net negative
  once re-scored honestly (cap=1: ×1.0574 naive → **×0.9457** lc-honest).
- The live agent is **already 79–85% single-action batches** (median 1, mean 1.64–2.20); it reaches
  ~11 actions per turn through 1.6–2.6 *sequential tool calls*, not one long batch.

Their concern: probe turns teach isolated single actions, i.e. push on the abundant behaviour and
erode the scarce one. **Measured, on the same 5 families:** single-action turns went 21.4% → **45.0%**.
Directionally they were right.

**But the measurement found something they did not predict and I had not looked for: the long tail
was already dead, and the probes had nothing to do with it.**

| | v0 (batch cap 8) | probes, cap 8 | **probes, cap 32** |
|---|---:|---:|---:|
| mean batch | 4.64 | 2.35 | **8.26** |
| max batch | 8 | 8 | **32** |
| single-action turns | 8.7% | 45.0% | **25.8%** |
| **turns with batch ≥ 15** | **0** | **0** | **6 (19.4%)** |
| `board_changed: False` events | 0 | 19 | **25** |

**`--batch-size 8` was the binding defect.** It structurally forbade the exact behaviour P2's evidence
says completes levels on ar25 and tu93. No amount of probe tuning could have surfaced that; it took
someone else's measurement of a different arm.

Raising the cap to 32 fixes **both** halves at once: the ≥15 tail exists for the first time (19.4% of
turns), single-action turns fall back to 25.8%, and the no-op probes survive. **New defaults:
`--batch-size 32`, `--noops-per-level 1`.** For scale: even at 45% the corpus was still far *less*
single-action than the live agent's 79–85%, so the contrast direction was never inverted — but 25.8%
with a real long tail is unambiguously the better teaching signal.

**On the lc-honest multiplier (their second ask): it is 1.0 here by construction, not by re-scoring.**
Six structural checks over the actual code paths [V]: the augmented plan is replay-verified against
the *original* `levels_cleared`; augmentation reverts to the unaugmented plan if that fails; a game is
dropped outright if the harness replay clears fewer levels; pruning is itself replay-verified. **No
corpus edit of mine can remove a level completion, so there is no lost level to re-score.** That is a
stronger guarantee than applying P2's correction after the fact — but their rule is exactly right for
any edit that *could* cut a completion, and if a future edit relaxes the gate, `p2_replay.py` is the
instrument to reach for.

**And the distinction they flag is worth restating, because I hit the same wall from the other side:**
actions per *analysis turn* is not actions per *batch*. P2's B4=11.11 was a turn statistic used to
justify a batch-level cap, which is why the premise collapsed. My equivalent was assuming a no-op
inside a batch would show as a no-op — `step_env` aggregates `board_changed` with `any()`, so it
reports `True` and teaches nothing. Same conflation, opposite direction, both silent.

### 12.2 The bug: a process boundary I wrote code straight through

```python
for base in _source_path_entries(BUNDLE_DIR):     # <-- both are NOTEBOOK cell-8 names
```

The setup command is `"$PYTHON" - <<'PYSETUP' … PYSETUP` — **a separate interpreter with its own

**This was findable locally and my validation missed it by one category.** The builder validated that

### 12.3 Fixed, and the class is now a build failure

3. **`_assert_names_resolve()` is now a build gate.** It walks the rewritten setup command's AST,
