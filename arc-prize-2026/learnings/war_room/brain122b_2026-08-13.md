### 1.2 Refinements (not refutations)

- **"byte-identical image preprocessing" is loose.** The *values* are identical, but the files

  `image_processor_type: Qwen2VLImageProcessorFast`, while the 27B ships `processor_config.json`

- **Our "27B" is `Qwen3_5ForConditionalGeneration` / `model_type qwen3_5`**, 64 layers, hidden
  5120, 4 KV heads, `compressed-tensors` FP8 — despite the dataset slug saying `qwen3-6-27b`.
  Both models are the same generation. Vocab is **248320 on both**, and the special-token ids

### 1.3 ★ NEW FINDING — the upstream snapshot is INCOMPLETE. Three files, not one, are wrong.

The census named one trap (the `preserve_thinking` line). Enumerating the dataset's **20 files**
turns up two more, and they are the kind that kill a boot:

```
.gitattributes  README.md  chat_template.jinja  config.json  generation_config.json
hf_quant_config.json  model-0000{1..9}-of-00009.safetensors  model.safetensors.index.json
preprocessor_config.json  tokenizer.json  vocab.json
```

- **`tokenizer_config.json` is ABSENT.** `AutoTokenizer.from_pretrained` would have to resolve
  the tokenizer class from `config.json`'s `model_type: qwen3_5_moe`, and every special-token
  *name* (`image_token`, `video_token`, `eos_token`, `pad_token`) plus `model_max_length` would
  be unavailable.
- **`processor_config.json` is ABSENT.** `AutoProcessor.from_pretrained` needs an image
  processor **and a tokenizer**; with no tokenizer config it has nothing to build the text half
  from. **This is the plausible hard failure for the multimodal path**, which is the half of the
  harness that matters (`MULTIMODAL_CONTEXT=current_grid`).
- (`merges.txt` and `special_tokens_map.json` are also absent, but harmlessly: `tokenizer.json`
  is a self-contained fast BPE — **247,587 merges inline, 26 added tokens**, and the ids match
  `config.json` exactly: endoftext 248044, im_start 248045, im_end 248046, vision_start 248053,
  vision_end 248054, image_pad 248056, video_pad 248057.)

**This does not contradict the census** — the census never claimed the file set was complete —
but it is the difference between a canary that boots and a canary that dies at minute 40 with
an opaque `AutoProcessor` traceback. **It is also cheap to fix, and the fix subsumes the
`preserve_thinking` trap** (§2).

## §2 — THE STAGING SHIM (one fix, three defects)

The canary stages a writable model dir before vLLM ever sees the weights:

1. link (symlink, hardlink fallback — **never copy**, it is 83.5 GB) every file from the
   read-only mount into `/kaggle/working/b122-model/`;
2. drop in **`tokenizer_config.json`**, **`processor_config.json`** and **`chat_template.jinja`**
   taken verbatim from the 27B we already serve, embedded in the notebook as base64
   (~13.5 KB total, so **the 27B does not have to be attached** — which also keeps the total
   attached input at 71.3 + 6.5 GB instead of ~107 GB, retiring census risk (iii));
3. re-assert, FAIL-LOUD: 9 shards present, `preserve_thinking` branch present in the staged
   template, `tokenizer_class` set, `processor_class == Qwen3VLProcessor`, staged quant is
   NVFP4/modelopt.

Substituting the 27B's chat template is **safe and preferable**: the two templates differ in
exactly two lines, so this restores the `preserve_thinking` branch (line 100) *and* reverts the
tool-arg serialisation line (122) to the exact behaviour our 100+ submissions were drawn under.
**One variable changes: the brain.** (Line 122 is the 122B being *more* correct; adopting it
would be a second, unmeasured change riding along.)

Shim provenance is pinned in the builder: `tokenizer_config.json` 1,165 B sha256
`792fa3f0cb88b111…`, `processor_config.json` 1,191 B `d89ef49ce9cd37fb…`, `chat_template.jinja`
7,764 B `e84f32a23fdda276…`; the builder refuses to run if any hash moves.

### 2.1 ★ Corroborated from the wheelhouse's own vLLM, before the run

Read directly out of `wheels/vllm-0.24.0-cp38-abi3-manylinux_2_28_x86_64.whl` (free download,
no GPU). Three things that could each have been a silent boot-killer are now settled on paper:

- **The architecture is registered.** `vllm/model_executor/models/registry.py` maps
  `"Qwen3_5MoeForConditionalGeneration" → ("qwen3_5", "Qwen3_5MoeForConditionalGeneration")`.
  It subclasses `Qwen3VLForConditionalGeneration` and is declared `IsHybrid` (the linear-attention
  path is a first-class citizen, via `layers/mamba/gdn/qwen_gdn_linear_attn`). **This also
  vindicates omitting `--kv-cache-dtype fp8`:** forcing a KV dtype on a hybrid model is exactly
  where unsupported-combination aborts live, and the KV term is too small to be worth the risk.
- **`modelopt_fp4` is a real quantization method** in this build — it is in the
  `QuantizationMethods` Literal alongside `modelopt`, `modelopt_mxfp8`, `modelopt_mixed`. The
  explicit flag will not be rejected as an unknown name.
- **★ THE SHIM IS NOT SPECULATIVE — it is required by this code path.**
  `Qwen3_5MoeProcessingInfo` inherits `Qwen3VLProcessingInfo`, whose `get_hf_processor()` builds
  a **`Qwen3VLProcessor`** through `self.ctx.get_hf_processor(...)`, and whose
  `get_video_processor()` demands a **`Qwen3VLVideoProcessor`** off that same object. Building a
  `Qwen3VLProcessor` needs a tokenizer *and* a video-processor config — and the upstream 122B
  snapshot ships **neither `tokenizer_config.json` nor `processor_config.json`**. The 27B's
  `processor_config.json` that we embed carries **both** the `image_processor` and the
  `video_processor` blocks. Without the shim, the most likely outcome is a boot failure inside
  `get_hf_processor` **after** paying the full 83.5 GB weight-load cost.

## §3.3 ★ THE CENSUS'S BANDWIDTH ARGUMENT IS OPTIMISTIC BY ~3×. The direction survives; the margin does not.

Prompted by the LoRA lane's gated-attention finding (Qwen3.5 packs q and its gate into one
projection, so `num_heads × head_dim` understates q by 2×), I checked what is actually quantized
in this checkpoint. **`model.safetensors.index.json`: 149,309 tensors, `total_size`
83,474,870,752 B — and exactly 36,864 `weight_scale` entries = 48 layers × 256 experts × 3
projections.** So **only the MoE expert weights are NVFP4. Everything else — the 36
`linear_attn` layers, the 12 `self_attn` layers, all 48 `shared_expert` blocks, the vision
tower, embeddings and `lm_head` — is BF16 on disk**, exactly as the 148-entry `ignore` list says.

Reconstructing bytes read per decode token:

| component | on disk | read per token |
|---|---|---|
| 256 experts × 48 layers × 3 × (3072×1024) = **115.96 B params** at FP4 + group-16 FP8 scales | **65.2 GB** | only top-8/256 ⇒ **~2.0 GB** |
| everything else = 83.47 − 65.2 = **18.2 GB BF16** (≈9.1 B params), of which the linear-attn stack dominates | **18.2 GB** | dense, read every token; less the vision tower (~1 GB, unused in text decode) and the embedding gather (~1.5 GB) ⇒ **~15.7 GB** |
| **total** | 83.5 GB | **≈ 17–18 GB/token** |

**The census says "10B active at 4 bits ≈ 5 GB per token — roughly 5× less traffic than the
model we run today."** The correct figure is **~17–18 GB**, because the *active* 10 B params are
overwhelmingly the BF16 dense ones, not the FP4 expert ones. Against the 27B-FP8's ~27 GB that
is **~1.5× less traffic, not ~5×.**

**This does not kill the bet — it re-sizes it.** The sign of the argument is unchanged (the 122B
still reads less per token than the incumbent, unlike the 72B-AWQ's ~36 GB which read *more*),
and the FP4 tensor cores still help on the expert matmuls. But "should comfortably beat the
incumbent" becomes "should be in the same neighbourhood as the incumbent, maybe somewhat
faster". **The pre-registered incumbent line (agg ≥ 192 tok/s) was therefore a harder test than
the census realised, and the bar line (≥ 40 tok/s) is the one that carries the decision.**

Caveats, stated: the vision-tower and embedding exclusions are estimates, and the index gives
byte totals rather than per-tensor shapes, so treat this as ±20%. **It changes no gate** — the
canary measures throughput empirically, which is precisely why the gate was written on measured
tok/s rather than on this arithmetic.

## §5.1 ★★★ RESULT — v1 = **INFRA DEATH**. No envelope reading. No throughput number.

`canivel/arc3-b122-boot-canary` v1 → **ERROR** after ~1 h. **This is NOT a reading on the brain**
and must not be recorded as one: the model was never loaded and no token was ever generated.

**Root cause, from `vllm-openai-server.log` (1,719 B — it died at import):**

```
File "/kaggle/working/vllm-site-packages/vllm/platforms/cuda.py", line 22, in <module>
  import vllm._C_stable_libtorch  # noqa
ImportError: libcudart.so.13: cannot open shared object file: No such file or directory
```

**vLLM 0.24.0 links CUDA 13. The Kaggle image ships CUDA 12.** The CUDA-13 toolchain therefore
arrives *only* as the pip wheels the wheelhouse pins (`nvidia-cuda-runtime==13.3.29` et al.),
which `pip --target` drops under `<SITE_PACKAGES>/nvidia/*/lib` — **a path the dynamic loader
knows nothing about**. The duck's `vllm_env()` sets `PYTHONPATH` and nothing else, which was
always sufficient for its own CUDA-12.8 build because the image already provided those `.so`
files on the default search path. **It is not sufficient for a CUDA-13 wheelhouse.** Nothing to
do with NVFP4, SM120, the 122B, or the shim.

**What v1 DID prove, and it is worth having:**
- **The staging shim works exactly as designed.** `/kaggle/working/b122-model/` came back in the
  outputs holding precisely the three shim files at precisely the right sizes — `chat_template.jinja`
  **7,764 B**, `processor_config.json` **1,191 B**, `tokenizer_config.json` **1,165 B** — and
  nothing else, because everything else is a symlink into `/kaggle/input` (which Kaggle does not
  export). That is the signature of a correct symlink staging on Linux.
- The 83.5 GB + 6.45 GB attach was **accepted** by Kaggle — census risk (iii) discharged.
- The wheelhouse resolved and installed into `vllm-site-packages` — the jcole75 layout patch
  (`wheels/` + `requirements-runtime.txt`) is correct.
- The rewrite, the GPU assert and the notebook structure all held; the failure is one line deep.

**FIX (v2, built and smoked, NOT pushed — both 08-13 slots are spent):**
`vllm_env()` now composes `LD_LIBRARY_PATH` from `_b122_cuda_lib_dirs()` — every
`<SITE_PACKAGES>/nvidia/*/lib`, `nvidia/*/lib64`, `torch/lib`, `cusparselt/lib` — **appending**
any pre-existing value rather than clobbering it. And `_b122_assert_cuda_runtime()` now runs
**after the wheelhouse install and before the weight load**, printing
`B122-CANARY cuda_lib_dirs=<n> libcudart=<paths>` and raising with the v1 error named if
`libcudart.so*` is still unresolvable. **v1 spent a GPU-hour to discover this; v2 spends about a
minute.** Smoke is now **72 passed / 0 failed**, with a `[C]` section that reproduces the v1
death (C1) and then proves the fix (C2–C7).

**Cost of the lesson:** ~1 GPU-h of the free 30/wk allowance, no cloud spend, no submission.
