## Summary (2 sentences)
The proposal's core moves — run the zero-draw bench A/B, refuse a TV28 redraw on n=1, and repair the ledger — are the right shape, and the document is unusually honest about its own instrument limits. But from a systems seat the plan is unpriced on the two axes I own: the bench session has ~zero wall-clock margin and consumes a large fraction of weekly GPU quota while being statistically incapable of delivering even the "kill" verdict it pre-registers, and the proposed dataset-version-pin fix may not be implementable through the toolchain the team actually uses.

## Objections

**[MAJOR] A 2v2 bench cannot license a kill — the best possible outcome has a one-sided permutation p of 1/6.** With n=2 per arm, even the strongest result (both B replicas beating both A replicas) has probability 1/(4 choose 2) ≈ 0.167 under arm exchangeability; using magnitudes doesn't rescue it, because the only variance estimate available (1.82/0.00, one pair, 1 dof) is worthless for a t-style read. The proposal says "the only conclusion it can license is 'stop', and only on a large gap" — but no gap at n=2/arm is statistically licensable, so the pre-registration as written is vibes with a number-shaped hole. Fix: either pre-register an explicit decision rule that admits its weak error rate ("complete separation B>A at 2v2 = directional evidence feeding a stop decision that also weighs the author's 10-graft null and his #207 board row"), or budget n=4/arm (p=1/70 on complete separation), which is 8 replicas ≈ 17.6 h ≈ two GPU sessions — a real quota decision that should be made explicitly, not defaulted.

**[MAJOR] The session wall-clock has zero margin and the quota cost is unstated — "0 draws" is not "free".** By the proposal's own [V-doc] evidence, every archived game ends on the 7920 s per-game wall clock, so 4 replicas ≈ 8.8 h of pure game time before model load (an FP8-repacked ~27B pulled off a Kaggle dataset mount is plausibly 15–40 min), engine warmup, and artifact write. If the platform session ceiling is ~9 h, the run dies after burning the whole budget with no `benchmark.json`; the v22 "commit run of 4 game-passes" precedent suggests it fits, but that precedent must be checked against the *current* per-game clock and bundle, not assumed. Separately, ~9 h is roughly a third of a weekly Kaggle GPU quota; the proposal prices the experiment at "0 submissions, 0 draws, ~30 min of edit" and never mentions quota, remaining hours, or what other planned runs it displaces. Fix: state the enforced session cap, the measured load/warmup overhead, and remaining weekly quota; if margin is <30 min, trim the per-game clock for bench (e.g., 6600 s — it's a paired comparison, both arms shrink identically) or run 3 replicas.

**[MAJOR] The version-pin remedy may be unimplementable as specified — and there is a stronger fix available.** The action item says "pin the dataset VERSION in `kernel-metadata.json`," but Kaggle's CLI `dataset_sources` field is documented and widely observed to resolve slugs to *latest* at run time; whether a `/versions/N` suffix is honored by the push-and-run path this team uses (CLI 2.0.0/2.2.2) is exactly the kind of thing that fails silently. If pinning isn't honored, every "pinned" redraw is still a floating config and the config-mean bookkeeping the deadline rule depends on is still broken while *believed* fixed — worse than known-broken. Fix: copy the 08-29 12:51 bundle bytes into a canivel-owned dataset (byte-hash recorded), mount that; regardless of pinning mechanism, have the kernel sha256 the mounted bundle at runtime and print it, so every draw self-identifies its code identity in its own log.

**[MAJOR] The "placebo" is clean informationally but not thermodynamically: arm A pays a token tax inside a hard wall-clock, and the bench conflates that tax with graft information value on one game.** Graft text lengthens context; longer context slows decode (the ~30.7 tok/s figure is context-dependent) and prefill eats wall time, so arm A gets fewer actions inside 7920 s than arm B *independent of whether the graft text informs anything* — and per the clockwatch finding, action count under the wall clock is the binding resource. For a ship/kill decision this tax is legitimately part of the treatment (submission pays it too), so it doesn't invalidate the comparison — but it does mean a B>A result on m0r0 cannot be read as "the graft *information* is useless," and the tax/value balance can differ by game, so single-game generalization is weak. Fix: have bench log per-arm actions-taken, generated tokens, and per-step latency so the two effects are separable in the readout, and pre-register that any kill applies to "13-graft stack as deployed," not to graft content.

**[MINOR] Don't run the experiment inside the production artifact.** Adding the `bench` flag and replica block to `canivel/arc3-tv28-fork` puts experiment code one guard-failure away from a real draw; the proposal's own gap list notes `install()` is blanket-guarded and falls back silently, i.e., guards in this stack are exactly the components that fail quietly. Fork a bench-only kernel copy; verify the `not TRUE_SUBMISSION` guard there; leave the submission kernel byte-frozen.

**[MINOR] Order effects in a single 9-hour session are uncontrolled.** Four sequential ~2.2 h games in one process can drift (KV/memory fragmentation, engine state, degraded late-session throughput); if the replica order is fixed A0,B0,A1,B1 that's partially interleaved, but confirm the engine is re-initialized per replica or that order is randomized, else position confounds arm at n=2 where a single bad replica decides the outcome.

## Questions for the authors
1. What is the enforced session ceiling for Save & Run on this competition's GPU image, what is the measured model-load + warmup time for the FP8 repack from the dataset mount, and what per-game wall clock will bench use? Show the arithmetic closes with ≥30 min margin.
2. State the numeric pre-registered decision rule for the 2v2 before the run: what pattern of four numbers triggers "stop TV28," and what error rate are you accepting on it?
3. Has anyone verified that a dataset version reference in `kernel-metadata.json` is actually honored at run time by your CLI push path, or is the self-owned byte-copy the plan?
4. Does `make_replicas` *replace* `bm.games` (4 games total) or append to it (more than 4 games, blowing the session budget)?
5. How many weekly GPU quota hours remain, and what other runs (bench rerun, any planned commit) compete for them this week?
6. Is the engine/process restarted between replicas, and is replica order randomized?
