## Objections

**[FATAL — unless the variance scales are reconciled] The H4 gate machinery is statistically unpowered within the window budget, by the proposal's own numbers.** The bootstrap gives 1-seed paired-Δ sd = 0.52; a 3-seed binding gate therefore has SE ≈ 0.52/√3 ≈ 0.30, while every effect the plan hopes to detect is +0.05 to +0.20. Detecting +0.12 at 80% power against paired sd 0.52 needs on the order of 150 seeds, not 3 — and with ~78 windows to Sep 30 (some already committed to control σ-draws), the budget cannot fund even one adequately powered gate, let alone gates for the port bundle, restart lever, and R2. The proposal itself flags the 7× discrepancy between σ̂_control (0.074, df 4) and the bootstrap sd (0.52) and then simply doesn't reconcile it: these cannot both describe the same instrument. Either show, with the actual gate estimator, that gate-level variance is genuinely near σ̂_control (in which case publish that measured SE and the derivation), or the plan's every ACCEPT/KILL decision is a coin flip and the plan as written is invalid. Required artifact: null-vs-null bootstrap of the *3-seed gate statistic exactly as it will be computed*, with P(false gate-pass) printed.

**[MAJOR] The wall-clock discount in R1b is a load-bearing free parameter that flips the decision, and it is not pinned in the pre-registration.** The exploratory table spans Δ = +0.22 (disc 1.0), +0.105 (0.6), +0.037 (0.365) against a kill threshold of +0.10 — the discount choice alone determines survival, yet §R1b never states which discount cell is binding, nor where 0.6/0.365 come from. Worse, "wall-cost cell from measured per-action wall in null10 histories" is an extrapolation: restart-heavy trajectories do not have the same per-action wall profile as null play (resets, re-traversal of cleared states, different inference context lengths), and it's unstated whether the per-action wall was measured on the pod or the Kaggle rail — the rails have already shown they disagree. Fix before running: (a) state the actual Kaggle per-run wall limit and current null utilization; (b) measure per-action wall from Kaggle-rail banner timestamps on restart trajectories specifically; (c) pre-register the single binding discount cell.

**[MAJOR] "Free" Kaggle is not free — the 30 h/wk quota and 2-push/day cap are never budgeted against the plan's own demands.** The plan simultaneously requires: daily control σ-draws, 2-seed screens, 3-seed gates per lever, port-bundle evaluation ("kit + build" = the full daily push quota), and the deployment submissions themselves — all on one rail declared "the binding instrument." No number is given for hours-per-seed, so it is impossible to verify that even one screen→gate→window cycle per lever fits in a week, and experiment traffic and scored-submission traffic are competing for the same ~78 windows without any allocation table. Required artifact: measured wall-hours per Kaggle-rail seed, and a week-by-week quota table (hours + windows + kernel pushes) through Sep 30 showing the R0 and R1b pipelines both fit with slack for failed pushes.

**[MAJOR] The pod↔Kaggle sign flip is relabeled, not diagnosed, and R1b still routes its kill decision through the discredited instrument.** Pod 3-seed Δ +0.169 vs Kaggle-rail 3-seed Δ −0.73 on the same config is a ~0.9 disagreement with opposite sign; declaring "pod = dev screen only" does not explain it. Yet R1b's first gate is "kill if held-out Δ < +0.10 **local**" — i.e., Kaggle-window spend is being allocated by an instrument with one measured, catastrophic, unexplained sign flip. Diagnose the mechanism (GPU class and token throughput, wall-limit truncation, environment/wheel version skew, model quantization differences between rails) with at least one controlled A/B before any local number is allowed to gate anything; otherwise both false kills and false promotions are live risks in both directions.

**[MAJOR] The $68 R2 reserve has an EV entry but no cost model.** "+0.19 × 0.15–0.3" is asserted with zero statement of what $68 buys: GPU type, $/hr, total hours, how many forensic transcripts + builds + validation seeds that funds — and whether the output can even reach a decision, given that H4 requires binding gates on the Kaggle rail anyway (so pod dollars buy only dev signal with the sign-flip risk above). At plausible RunPod rates ($1.5–2.5/hr for a usable card) this is ~27–45 GPU-hours total, which likely does not cover 3-seed anything. The promised "decision table before first forensic transcript" must include this cost model or R2's EV line should be struck from the targets.

**[MINOR] Single-day, zero-slack kernel-push scheduling.** Jul 14's port-bundle path needs exactly 2/2 daily pushes (kit + build); one failed push, OOM, or dataset-mount error slips the day and burns a window on filler. Pre-stage the kit push the prior evening or explicitly accept the slip cost in the ledger.

**[MINOR] Exploratory EV is driven by 3 games in a 10-run corpus.** Gains concentrate in ft09/tn36/tu93; a 10-null-run corpus with heavy-tail concentration means the seed-split in R1b (select on 1–5, estimate on 6–10) may have zero deep-recovery events in the estimation half. State up front what R1b reports if the held-out half contains no recovery events (it should report "no information," not Δ=0).
