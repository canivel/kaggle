## Summary (2 sentences)
The proposal is unusually well-instrumented (local A/B harness, pre-registered kill criteria, hard process gates) but its private-set thesis rests on a load-bearing capability claim it never tests: that an in-kernel 27B coder can run a Rodionov-style world-model-synthesis loop that was validated only with frontier models, and whose "de-risking" was performed offline by Opus — a different model class under a different budget. Worse, the deterministic-search differentiator (BFS "owning 14 games") appears to depend on per-game engine clones that cannot exist for the private set, which means the two headline differentiators collapse into a single untested dependency on Phase 2.

## Objections

**[FATAL] The private-set differentiators reduce to one untested dependency — 27B runtime model synthesis.** `bfs_solve()` is described as an "engine-clone solver, load-bearing on 14 games," but engine clones were built offline, per public game, by Opus over 10h/7M tokens. On the private ~55 games no such clones exist, so BFS-through-a-model works *only if* the Phase-2 runtime Rodionov loop produces Class-A models in-kernel — the exact capability kill-criterion P2 admits may fail. If P2 fires, the surviving system is duck + `explore()` + voting: a well-run fork in the 1.0–1.3 mid-pack band the proposal claims to escape. The thesis "general-by-construction" is therefore not by construction; it is conditional on the plan's single weakest assumption. Fix: state explicitly what `bfs_solve()` searches over on an unseen game, and restructure Phase ordering so the 27B-synthesis question is answered *first* (see next objection).

**[MAJOR] The Rodionov de-risking is a category error, and the fix costs one afternoon.** "22/24 Class-A sims" de-risks the *verification methodology* using a frontier model with unbounded offline iteration; it says nothing about Qwen 3.6 27B FP8 writing and refactoring transition models inside a 60s tool-loop, 32k context, and 2.2h/game. Risk #2 acknowledges this ("GPT-5.5… likelihood high") but the mitigations — "sim-template scaffolds, MDL-style prompts" — are precisely the 'we will prompt it better' hand-waving this panel exists to reject. The decisive experiment is cheap and available *now*: on the RunPod A40, feed Qwen 27B the recorded transition histories from 5–10 public games plus the template library, and measure Class-A rate under runtime-realistic token/turn caps. This should be a Phase-0 gate, not an Aug 17 discovery; three weeks of Phase-2 slots hang on it.

**[MAJOR] The LLM-routed tool delegation is the weakest known pattern in the design, presented as the default.** "Goal understood → bfs; goal unknown → explore()" requires a 27B to self-assess goal comprehension — small-model calibration on "do I understand?" is notoriously poor, and a confidently wrong "understood" burns budget in BFS over a wrong objective. The proposal's own fallback (scripted `explore()` trigger after N no-progress turns) is the more robust architecture and should be the primary, with LLM routing as the A/B-tested variant, not vice versa. Additionally, grafting three tool APIs into Duck's prompt changes the very prompt distribution that produced 1.21 in a system its own author calls variance-dominated; the "no game regresses >1 level in 2/3 seeds" guard is underpowered to detect tool-distraction regressions (see next objection).

**[MAJOR] No context/token accounting for a 32k window that must now hold five competing payloads.** Duck's prompt + tool schemas for three new tools + persisted archive state + distilled cross-level world model + few-shot sim templates (which are *code*, i.e., long) + the transition history the Rodionov loop must reason over. No arithmetic is given; Risk #5 names the problem and answers with "truncation and caps," which is a mechanism, not a budget. Fix before Phase 1: a per-turn context budget table (tokens per component, worst case), and a decision on what gets evicted when the WM loop and the archive both want the window.

**[MAJOR] Success criteria are pre-committed before the variance they must exceed is known.** Phase 0 measures local 3-seed std; Phases 1–3 already fix thresholds (+3, +4, +2 levels aggregate). If duck's local per-seed spread is comparable to these deltas — plausible given the author couldn't reproduce his own 1.21 — then 3 seeds cannot distinguish a merged "verified win" from noise, and the "we measure, they gamble" differentiator quietly becomes gambling with better bookkeeping. Fix: after Phase 0, pre-register a paired per-game test with an explicit power calculation; if 3 seeds are insufficient, the 8 GPU-h/sweep cost says 5–7 seeds are affordable and should be mandated.

**[MINOR] "Restart-with-carried-notes" voting can propagate confabulation.** Carried notes are LLM-authored summaries; a wrong world-model belief written into notes poisons every subsequent attempt, converting independent draws into correlated ones and undermining the variance-reduction claim. Ablate notes-carried vs. clean-restart voting in Phase 2 before crediting voting with the 30% variance reduction.

**[MINOR] Local A40 harness ≠ Kaggle kernel environment for a trajectory-sensitive agent.** vLLM version, sampling defaults, and wall-clock timing differences change agent trajectories, so local paired deltas may not transfer. One cheap check: run the identical frozen build locally and on Kaggle 3× each and report the cross-environment rank correlation of per-game levels before trusting local gating for submission selection.
