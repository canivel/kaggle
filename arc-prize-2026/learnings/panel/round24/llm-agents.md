# R24 review — reviewer "llm-agents" (Professor of LLM Agents and Scaffolding)

## Summary

The lane decision is right — compaction is dead for a mechanism-level reason, three teams converged on state-externalisation, the duck already has the programmatic single-`python`-tool substrate, and spending two $0 offline falsifiers (S1/S1b) before the one push is exactly the correct order of operations. But the one push it authorises, arm P1, **cannot fail informatively as scoped**: the harness tells the model *five separate times*, including twice inside the tool schema itself, that its Python is ephemeral, and §6 explicitly retains all of it ("nothing is removed from context") while adding one contrary sentence to the system prompt — so a `namespace_reuse_rate < 0.15` reading would measure instruction conflict, not substrate capability, and the lane's headline falsifier can only produce a false negative.

## Objections

**[FATAL] P1's mechanism is a prompt change that the proposal forgot to read the existing prompt for; K4 can only fail invalidly.**
§6 scopes the arm as "Patch surface: `python_tool_sandbox.run_sandboxed_python` only … One sentence added to the system prompt … **Nothing is removed from context**." The substrate contradicts that sentence in five places, all of which §6 therefore keeps: `prompts.py:80` "Every `python` tool call starts fresh. Re-import modules or **re-define any custom utility logic you need**"; `prompts.py:82` "call it with one **ephemeral** `code` string"; `prompts.py:107` "The `python` tool code is **not saved between calls**, so rewrite any custom utility logic you still need"; `tool_agent.py:230` (`_PYTHON_TOOL_DESCRIPTION`) "Run one **ephemeral** Python snippet…"; and `tool_agent.py:1347`, the `code` parameter's own JSON-schema description, "The snippet is **ephemeral and is not saved across tool calls**." A sixth string, `prompts.py:113` ("Keep code snippets short and purpose-built rather than **dumping large frameworks into one call**"), actively discourages the artifact-building behaviour P1 exists to elicit. For a tool-calling model the *tool schema* is the highest-authority channel — it is re-serialised into every request, it is what the model is trained to condition its call format on, and it is the last thing before the call site; a single system-prompt sentence upstream of a 65K-token context will lose to it in a 27B open-weight model far more often than not. The consequence is asymmetric and disqualifying: P1 can **pass** validly (≥0.15 despite the contradiction is a genuine lower bound) but it **cannot fail** validly, because the pre-registered reading of K4 ("27B does not use the substrate", lane NULL, reallocate) would in fact be measuring "27B obeyed its tool schema over one contradicting sentence." A falsifier that can only yield a false negative is not a falsifier, and this is the *only* non-score falsifier the lane offers for its substrate half. **Fix (mechanical, $0):** rewrite all six strings as part of the arm — `_PYTHON_TOOL_DESCRIPTION`, the `code` parameter description in `_tools()`, and the three `prompts.py` lines — declare that diff in the prereg as the mechanism's prompt surface, and byte-audit it; then the K4 NULL reading becomes legitimate.

**[MAJOR] The arm-defining invariant in §6.1 is self-voiding: it is unsatisfiable by any arm that changes a prompt or tool string.**
§6.1 demands the trimmed-message sequence from `_trim_messages_for_context()` be "byte-identical to baseline on every event," else the run is VOID. But `_trim_messages_for_context` returns `[system_message, *history]` with `system_message = messages[0]` (`tool_agent.py:1759`, `:1767`), so changing the system prompt makes the output non-byte-identical **by definition**; worse, the trim loop's stopping condition is `self._estimate_request_input_tokens([system_message, *history], tools=tools) > budget_tokens` (`:1763`), with `tools` passed in from `_tools()` — so editing the tool description changes the token estimate and can flip a drop decision at the margin. As written, P1 voids itself on event 1. This is not pedantry: the invariant is the structural guarantee §6.4 offers against the M3 confound, and it is the one thing A22 "bought us." **Fix:** restate it as a *policy* invariant — the eviction/drop policy, `evicted_chars`, and the **count and identity of dropped history blocks** must match baseline on every event, with the only permitted message-sequence diff being the fixed, pre-registered prompt/tool-schema delta; add a pre-registered headroom assertion that the added tokens never flip a drop decision, and report any event where they do as a live confound rather than silently absorbing it.

**[MAJOR] `namespace_reuse_rate` is an unspecified instrument carrying a pre-registered numeric threshold — the exact error class that just cost the campaign the M3 attribution.**
"Fraction of turns that reference a name defined in a *previous* turn" has two natural implementations that give **opposite verdicts on the same transcript**. Reading A (any name that also appeared in a previous turn) is satisfied by the model re-defining `bfs` every turn — which baseline transcripts show it does constantly — so K4 passes vacuously and measures nothing. Reading B (names *loaded without being bound in the current turn*, resolved against the previous turns' bindings) is the meaningful one, and reads ~0.00 at baseline by construction. The proposal never says which, never specifies the extractor (AST vs regex), and never excludes the harness-injected globals that are rebound every call by `_refresh_state` — `current_frame, previous_frame, latest_frame, history, transitions, last_transition, last_action_frame, last_action, valid_actions, last_action_result, action, result` — several of which a lazy implementation will score as "defined in a previous turn." The floor **0.15 is also unanchored**: no baseline value, no synthetic-positive value, no derivation. §5.4 schedules a transcript-forensics pass but does not make it blocking on S2 or tie it to this number. **Fix ($0, workstation, before seal):** specify Reading B with an AST-based binder/loader analysis and the explicit harness-global exclusion list; validate on `war_eval_v1`'s 1,686 turns where it MUST read ≈0.00 (specificity) and on a hand-built positive (sensitivity); then derive the floor from the measured *redefinition* rate (how often a turn re-authors a function body a previous turn already authored) rather than asserting 0.15.

**[MAJOR] The declared patch surface is understated in three places, on a campaign with five provenance-drift ERROR submissions.**
`run_sandboxed_python` is not where persistence lives. The child is `subprocess.Popen([sys.executable, "-I", "-S", "-c", _SANDBOX_BOOTSTRAP])` and `_SANDBOX_BOOTSTRAP.main()` is **single-shot by construction** (`python_tool_sandbox.py:310–396`): it `_recv()`s one payload, `exec`s it, `_send`s `final`/`error`, and returns — the process then exits. Persistence requires rewriting that module-level bootstrap string into a recv/exec/send loop, which is a protocol change, not "lifecycle." Three further items sit outside the declared surface: the per-call `tempfile.TemporaryDirectory` that is the child's cwd (`:455`), the host-side single-shot `deadline` loop (`:499`), and — per the FATAL above — `prompts.py` and `_tools()`. Addendum §A4 records that the top three failure families are build/provenance-infra modes and that `provenance:scratch-built` produced five ERROR incidents; understating the diff at seal time is precisely how that path is re-entered. State the true surface in the prereg and byte-audit it. (The proposal's `RLIMIT_CPU` per-call→per-game warning is correct and well spotted; note `_set_limits` also pins `RLIMIT_FSIZE` and `RLIMIT_NOFILE` once at child start from the *first* call's timeout, `:252–267`.)

**[MAJOR] The lane's artifact schema is not constructible in the lane's substrate.**
§3(a) defines the artifact as "Tycho's `State` **dataclass** + `init_state`/`transition`/`render`/`outcome`, with `UNKNOWN=-1` abstention." The sandbox's `SAFE_MODULES` allowlist is `bisect, collections, copy, fractions, functools, heapq, itertools, json, math, operator, random, re, statistics, string` (`python_tool_sandbox.py:42–57`) — **no `dataclasses`, no `typing`, no `enum`** — and `prompts.py:81` recites that allowlist to the model verbatim. `_safe_import` raises on anything else. So the typed artifact either degrades to dicts/`namedtuple`s (say so, and re-check that the falsifiability argument survives the degradation) or the allowlist must be extended — a fourth undeclared patch-surface item with its own risk review. Nobody appears to have tried to write the artifact against the real sandbox before proposing it as the lane's centrepiece.

**[MAJOR] §3(b)'s load-bearing [V-ours] claim is inaccurate, and the correction changes P3's design.**
The proposal states the digest "`world_model, goal_model, action_model, recent_findings, open_questions, current_plan, cross_level_notes` is **wiped** on level transition and game over." The code wipes six of those seven: `_update_summarized_knowledge_from_step_summary` (`tool_agent.py:1188–1201`) resets `world_model, goal_model, action_model, recent_findings, open_questions, current_plan` — and **deliberately excludes `cross_level_notes`**, which survives every transition. The duck's authors therefore already built a designated cross-level carrier and chose to reset only the level-specific models. P3 is thus not repairing an oversight, it is *reversing a design decision*, and a blanket un-wipe is the weakest version of it. Addendum §A3's refinement from Feng — consolidate a cross-level policy at first level-clear, then **refine rather than rewrite** — is the correct shape and it maps directly onto the existing `cross_level_notes` slot. Amend §3(b) and §4-S4 accordingly. (Addendum §B5's "do not build a typed/relational graph for P3; keep it flat" is consistent and should be folded in.)

**[MAJOR] The S2-before-S4 ordering (P1 namespace before P3 memory) is not supported by our own strongest evidence, and the packet addenda push the other way.**
The proposal's case for lane (a) rests entirely on three frontier-model external results and never cites `learnings/war_room/transcript_forensics.md`, which is the best in-house evidence in the repo and whose *first* cross-cutting fix is "**Persistent per-game hypothesis ledger** (proposed / refuted / evidence) injected each turn" — i.e. P3, not P1. That document's observed waste is natural-language re-derivation (lp85: "8+ consecutive analysis-only turns … re-deriving the same 3-row layout from ascii each turn"; su15: "near-verbatim repeated paragraphs ≥3×"; sb26: SPACE re-probed 8–20×/run), which a Python namespace only captures **if the model chooses to read back from it** — the very affordance-trigger risk 2608.04828 flags. Addendum §A3 adds the only 27B-on-our-substrate precedent in three sweeps and it is a *memory* solution, not a namespace one. P3 is also cheaper (S, ~1 cycle) than P1 (M, 1–2 cycles plus the RLIMIT/lifecycle/bootstrap hazards above). The stated justification for putting P1 first is that it has a cheap decisive falsifier — but per the FATAL that falsifier is currently one-sided. Either repair K4 first (then P1-first is defensible) or swap S2 and S4 and say why in the minutes.

**[MINOR] Addendum §B3 is over-read as support for P1, and its second-hand caveat is moot on our substrate.**
2608.06370 finds programmatic tool calling beats JSON, +5.5% under context flood. The duck is **already** programmatic — one tool, `{"name":"python","parameters":{"code":…}}`, with `action()` called from inside the snippet. The paper therefore endorses the status quo and says nothing about *statefulness*, which is the only thing P1 changes; §B3's "independently supports the substrate half of lane (a)" is true but action-free. Its own caveat (zero open-weight models) is correctly stated. The flagged second-hand "filesystem store degrades 32% → favours in-process namespace over Tycho workspace files" should be struck rather than merely flagged: our sandbox has no `open` in `SAFE_BUILTINS`, `RLIMIT_FSIZE` is 1 MB, and the cwd is a per-call `TemporaryDirectory` — a filesystem store was never an option here, so the comparison cannot inform our design either way. §B7's code-well-formedness pre-mortem, by contrast, is the genuinely useful item and should be adopted.

**[MINOR] Persistence introduces a new silent-wrong-state failure mode that baseline does not have, and it lands on the primary gate.**
With a shared `runtime_globals` across turns, a turn that raises mid-`exec` leaves **partial bindings** behind (the bootstrap catches at the top level and returns; names bound before the exception survive). Turn N+1 can then read a half-updated world model with no error, and act on it — under a quadratic action penalty. Baseline is immune by construction. Additionally `SAFE_BUILTINS` contains only `Exception, TypeError, ValueError, RuntimeError`, so the model **cannot write `except NameError:` or `except KeyError:`** — stale-reference recovery is unavailable to it. Pre-register the semantics (transactional rollback of the namespace on a raised turn, or accept-and-log with a `partial_binding_events` counter) so that a §6.2 non-harm FAIL cannot be silently attributed to the substrate hypothesis when it was caused by this.

**[MINOR] §5.2's "field is quiet" premise, and §3(c)'s, are contradicted by the packet.**
Addendum §B2 withdraws the banking-field quietness claim outright (~20-paper skill-library/self-evolution cluster logged nowhere in `learnings/`) and requires (c)'s down-ranking to rest on the generalisation rail instead. The proposal should be amended in those words before §5.2 is sealed. Note that §B6's "third consecutive quiet compaction sweep" is a *different* claim and does survive, so the A22 death record is sealable as written — but the two must not be conflated in the minutes. Also, §6.5's arithmetic is one draw stale (n=26, threshold 1.0773 per §A1); harmless since no draw is requested, but fix it.

## Questions for the authors

1. Did anyone read `prompts.py` lines 76–114 and `_PYTHON_TOOL_DESCRIPTION` before writing §6's "one sentence added to the system prompt … nothing is removed from context"? If yes, what is the argument that one system-prompt sentence overrides five contrary statements, two of them in the tool schema, in a 27B open-weight model?
2. Which reading of `namespace_reuse_rate` is intended — "name also appears in a previous turn" or "name *loaded* in this turn without being *bound* in this turn"? What does the instrument read on the `war_eval_v1` baseline transcripts under each reading, and what is the derivation of 0.15 as opposed to 0.05 or 0.40?
3. Rather than relying on prompting at all: why not put the affordance in the **observation channel** — append a one-line footer to every tool result, `session namespace: <live model-bound names>` — so the model is shown, every turn, that its state survived? That is a mechanism, not an exhortation, it is measurable, and it directly attacks the 2608.04828 null mode. If adopted, how does it interact with the §6.2 pinned `LOCAL_ANALYZER_TOOL_OUTPUT_TOKENS=1024` cap?
4. Has anyone written the Tycho `State` artifact against the actual sandbox allowlist (no `dataclasses`, no `typing`, no `enum`)? If it degrades to dicts, does the abstention/coverage falsifiability argument in §6.4 survive the degradation?
5. Given `cross_level_notes` is already exempt from the wipe, what exactly does P3 change — and why is that not a strictly cheaper and better-evidenced first push than P1?
6. What is the pre-registered semantics for partial namespace bindings left by a turn that raised, and will `partial_binding_events` be reported alongside the fallback count?
7. Feng (§A3) runs our exact substrate at 27B with persistent cross-level memory and ranks **177th, below our 1.33**. It is confounded and un-ablated and must not be read as efficacy evidence either way — but it is the only on-substrate, on-scoreboard datapoint we have. What prior does the lane place on P1+P3's *effect size* on the Kaggle metric, and does the panel record that this datapoint does not raise it?
8. Will the S1/S1b runnability check (§A6 flags it unverified) gate the S2 push, or run in parallel?

## What I cannot judge

- Whether 16 concurrent long-lived sandbox children are viable inside the Kaggle kernel's memory and process budget, and whether the orphan-reaping and `RLIMIT_CPU` re-accounting can be made reliable — systems reviewer's call; I only note the bootstrap rewrite it implies.
- The statistical adequacy of the paired seed-1 build-rail design, the n=26 ledger arithmetic, the stationarity verdicts, and whether mean Δlc ≥ −0.128 has adequate power — methodology's remit.
- Whether L0's "carrier set expands beyond ~4 games" is the right bar for the exec-wm simulators, and the substance of the `prune_trace` phase-desync root cause in (c) — prog-synthesis and RL/planning respectively. I note only §A4's observation that (c)'s root cause has **no fingerprint in the store at all** while carrying the largest diff surface of the three.
- Whether Tycho's, Schema's, and Prime Agent's self-reported numbers are trustworthy beyond the [SR] de-rating the proposal already applies; I accept the de-rating as sufficient and endorse §5.3.2 as standing policy (§B5's 44pp inflation figure strengthens it).
- The §5.3.1 zero-budget ruling on workstation LLM authoring. It reads as reasonable and §A3 supplies an external precedent (Feng discloses Codex co-authorship); it is a governance question, not an agents question.

## Verdict: MAJOR-REVISION

To be explicit about why this is not reflexive, and to make it terminating: **the lane selection (a), the Tycho-as-schema / (b)-as-component / (c)-on-its-own-clock structure, the ordering constraint "no eviction before verified externalisation," the §5.3.2 provenance de-rating, the §5.2 A22 death record, and the authorisation of S1 and S1b are all correct and should be ratified and executed today, unamended.** My vote turns solely on the **one push, S2**, whose stated scope guarantees an uninterpretable null on the lane's only non-score falsifier. The revision I require is finite, cheap, and closes at R25 or a sealed weekday disposition — nothing here needs another full panel:

1. Rewrite the six ephemerality/anti-framework strings (`prompts.py:80,82,107,113`; `_PYTHON_TOOL_DESCRIPTION`; the `code` param description in `_tools()`) as part of P1's declared and byte-audited patch surface; add the tool-result namespace footer or state why not.
2. Restate §6.1 as a drop-policy invariant with a token-headroom assertion, since byte-identity is unsatisfiable.
3. Specify and validate the `namespace_reuse_rate` instrument on existing baseline transcripts ($0) and derive the floor from the measured redefinition rate before sealing it.
4. Declare the true patch surface (`_SANDBOX_BOOTSTRAP` loop, tempdir/deadline lifecycle, prompts, `_tools()`, and any `SAFE_MODULES` extension the artifact needs); correct §3(b) on `cross_level_notes`; adopt §B2's withdrawal wording; either repair K4 before P1 or swap S2/S4.

Meet those four and I vote ACCEPT without further objection.
