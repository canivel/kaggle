## 1. Living-Harness Is an Interactive-Agent Evolver  ⭐ MOST RELEVANT (A22 lane)
- arXiv:2607.26598 (v1 2026-07-29; new-to-us this window) — https://arxiv.org/abs/2607.26598
- Takeaway: A **self-evolving, inference-only** agent harness. After each episode it converts
  the completed trajectory + evaluator signal into "posterior evidence for bounded harness
  updates" via an Evolution-SOP. It evolves exactly two procedural stores while keeping **tools
  and base context frozen**: (a) an **episodic memory of failure patterns and recovery actions**,
  and (b) a **state graph recording repair edges and transition rules**. Reports +10.07 / +9.91
  pts Pass@1 over the strongest interactive baseline on τ²-Bench (8 interactive envs) and
  MultiWOZ-2.4. The evolved state supports **retrieval-only reuse across different model
  backbones**. No RL / no fine-tuning.
- **Verdict: ADAPT (design input to the A22 arm; single strongest new item).** This is the
  closest published analog to what A22 is trying to do, and it lands squarely inside our
  constraints: inference-only (budget-legal), tools+base-context frozen (private-track-legal —
  no code-exec required), and single-model-compatible (retrieval-only reuse means the evolved
  store is model-agnostic). The load-bearing distinction from our shelved EWM+banking lane and
  from MemHarness's "reconstruct-not-replay" caution: Living-Harness does **not replay verbatim
  trajectories** — it distills *failure→recovery edges* and *transition rules* into a state graph
  and an episodic index, which is exactly the reconstruct-to-structure form the latent-state
  audit demands. Two concrete takeaways for the A22 prereg: (i) frame the retained-reasoning
  content as a **failure→recovery episodic index + state-transition graph**, not a running plan
  summary (directly answers the Plans-Don't-Persist "plans don't persist as state" problem — a
  transition graph *is* state, a plan blurb is not); (ii) the τ²-Bench harness is public and
  interactive — mine it for a distillable within-9h-wall update rule. Caveat: results are on
  τ²/MultiWOZ (tool-dialog), not ARC-AGI-3, and the +10pt is vs a self-improving baseline, so
  treat as a design pattern, not a transferable number. **Changes nothing on today's seal;**
  file as an A22-arm design amendment for R23.

## 2. MemoHarness: Agent Harnesses That Learn from Experience
- arXiv:2607.14159 (2026-07; new-to-us; code: github.com/HowieHwong/MemoHarness) —
  https://arxiv.org/abs/2607.14159
- Takeaway: Adaptive harness-optimization framework that learns from its own executions.
  Decomposes the harness into **six editable control dimensions** (context, tool, generation,
  orchestration, memory, output) and stores per-case diagnoses + distilled global patterns in a
  **dual-layer experience bank**. At eval it specializes the harness per test case using
  retrieved experience **without test-time labels, feedback, or extra search**. Inference-time
  adaptation, no per-case supervision. (Companion evaluation-methodology paper: "Rethinking the
  Evaluation of Harness Evolution for Agents," 2607.12227.)
- **Verdict: IGNORE for build (ADAPT as a framing reference for A22).** Useful as a taxonomy —
  it names the six harness surfaces our compaction+retained-reasoning arm actually touches
  (context + memory + generation), which sharpens how we describe the A22 intervention and
  isolates it as a single-surface change (context/memory) rather than a whole-harness rewrite.
  But the full framework is a per-case harness search that's heavier than the 9h wall and the
  single-config submission want, and its adaptation gains overlap conceptually with
  Living-Harness (which is the cleaner, more portable instantiation). No build; taxonomy citation
  for the A22-arm record.

## 3. Agentic Context Management (validated compaction: linear vs quadratic cost)
- arXiv:2607.21503 (v1 2026-07-23; new-to-us) — https://arxiv.org/abs/2607.21503
- Takeaway: Decomposes context management into **five primitives** (architecting, ingesting,
  scoping, anticipating, compacting & consolidation) and argues **naive accumulation grows token
  cost quadratically** in conversation length while **only *validated* compaction achieves
  linear cost with preserved fidelity** — crude summarization is linear but sacrifices accuracy.
  Reports 92% LongMemEval / 93.2% LoCoMo. Appears training-free (reference impl is a post-hoc
  multi-tenant service).
- **Verdict: IGNORE (compaction-lane reference; reinforces the A22 spec, no drop-in).** This is
  the third independent source (with OpenAI's compaction result and Addressable Recall Compaction
  2607.25066) making the same point the A22 arm is built on: **validated/lossless compaction >
  lossy summarization**, and the cost argument (quadratic→linear) is a clean justification for
  why compaction matters under the 9h wall specifically. But its results are on long-memory QA
  benchmarks, not interactive ARC, and it presupposes a "validation" oracle the duck harness
  doesn't expose. Keep on the compaction reference shelf alongside 2607.25066; use the
  quadratic→linear framing in the A22 rationale.

## 4. vLLM Qwen3 tool-calls-lost-inside-`<think>` (Issue #39056) — 72B postmortem watch
- github.com/vllm-project/vllm/issues/39056 (opened 2026-04-06, **still OPEN**) —
  https://github.com/vllm-project/vllm/issues/39056
- Takeaway: With `--reasoning-parser qwen3 --tool-call-parser qwen3_coder` on vLLM 0.19, when the
  model emits `<tool_call>` XML **inside `<think>`**, the reasoning parser strips everything up
  to `</think>` and the tool parser only sees post-`</think>` content → **populated reasoning,
  empty `tool_calls`.** Proposed parser-side fix (PR #39055) promotes embedded tool-call blocks
  out of reasoning into content. Related: a merged fix (vllm #35687, 2026-04-24) treats
  `<tool_call>` as an implicit reasoning-end for the qwen3 parser; open parser bugs #40785
  (qwen3_coder) / #40787 (qwen3_xml).
- **Verdict: IGNORE for the dead 72B route; NOTE as a live guardrail for any Qwen3-family
  retry.** This is the first serving-side item that is *mechanistically adjacent* to our
  livelock — "reasoning populated, native tool_calls empty." BUT it is **not the same failure**:
  ours was the model emitting **0/1044 native calls deterministically** (model-side format
  livelock, confirmed by the v5 forced-tool_choice boot passing), whereas #39056 is a *parser*
  that *drops* tool calls the model *did* emit inside `<think>`. So it does **not** reopen the
  72B route (that route is dead on a model-side, not parser-side, cause). Its standing value:
  **if we ever run any Qwen3 model with reasoning enabled, the qwen3/qwen3_coder parser can eat
  tool calls emitted inside `<think>` — a config trap to pre-empt (prefer qwen3_xml, or ensure
  tool calls land outside the reasoning span, or use forced tool_choice).** Guardrail note for
  the serving playbook; no change to the postmortem.
