### 3.3 The architectures are identical — the *quantization* is not

Full key-by-key diff, `vrfai/Qwen3.6-27B-FP8` vs `Qwen/Qwen3.8-27B-FP8`:

| Section | Differing keys |
|---|---|
| `text_config` | **NONE. Zero keys differ.** (64 layers, 48 `linear_attention` / 16 `full_attention`, `hidden_size` 5120, `head_dim` 256, `max_position_embeddings` 262144, `mtp_num_hidden_layers` 1, `rope_theta` 1e7 — all identical) |
| `vision_config` | `model_type` string only (`qwen3_5_vision` → `qwen3_5`), plus an absent `dtype` |
| top level | `transformers_version` (`5.6.2` → `5.8.0.dev0`), absent `dtype` |
| **`quantization_config`** | **everything — see below** |

**Ours (`vrfai`, `recipe.yaml` verbatim):** `compressed-tensors`, `format: float-quantized`,
scheme **FP8 W8A8 per-tensor static** (`strategy: tensor`, `memoryless_minmax`), llm-compressor
`0.14.0.1`, with `lm_head`, `embed_tokens`, `visual.*` and **`linear_attn.*`** left in BF16.

**Theirs (`Qwen/Qwen3.8-27B-FP8`):** `quant_method: "fp8"`, `fmt: "e4m3"`,
`activation_scheme: "dynamic"`, **`weight_block_size: [128, 128]`**, 882 `modules_to_not_convert`.

Note this is a *deliberate* divergence by our upstream, not an accident of timing: the official
`Qwen/Qwen3.6-27B-FP8` **also** uses `weight_block_size: [128,128]`, and Tufa/vrfai nonetheless
shipped their own per-tensor `compressed-tensors` re-quantization and attached *that*. **Their
reason is NOT ESTABLISHED**, but the fact that the block-FP8 variant of the *current* model was
available and not used is on the record.

### 3.4 What the format change does inside vLLM 0.19.0 — and the SM120 problem

`weight_block_size` being non-`None` flips `Fp8LinearMethod.block_quant = True`
(`fp8.py:287–288`) and routes every Linear through `W8A8BlockFp8LinearOp`, which picks a backend at
construction (`fp8_utils.py:553–585`) in this order: **cutlass → aiter → Triton fallback**, with a
separate DeepGEMM fast path gated at `fp8.py:438`.

Our card is **SM120** (compute capability 12.0; the Kaggle RTX PRO 6000 — established in-repo at
`ITERATION_LOG.md:971`, where FlashInfer refused arch 12.x).

- **DeepGEMM — OFF, proven from source.** `vllm/utils/deep_gemm.py:87–92` requires
  `current_platform.support_deep_gemm()`; `vllm/platforms/cuda.py:515–517` defines it as
  `is_device_capability(90) or is_device_capability_family(100)`; `vllm/platforms/interface.py:337–349`
  implements the family test as `capability.to_int() // 10 == capability // 10`. For SM120 that is
  `120 // 10 = 12`, against `100 // 10 = 10` → **False**. The docstring says "Hopper and Blackwell",
  but the code means **SM90 and SM10x only — SM120 is excluded.**
- **CUTLASS block-FP8 — NOT ESTABLISHED.** `w8a8_utils.py:21–28` delegates to the *compiled* op
  `ops.cutlass_scaled_mm_supports_block_fp8(capability)`. This is a C++ symbol; it is **not
  answerable from Python source and not answerable without booting the wheel on the card.** I will
  not guess it.
- **Triton fallback — exists, so it will not crash.** `fp8_utils.py:585` `return self._run_triton, ...`.
  It is the slowest of the three backends.

**Why that matters more here than it would elsewhere:** our binding constraint is
**action-count efficiency**, not reasoning quality alone (`learnings/daily_brief_2026-08-12.md:137`).
A GEMM path that is materially slower than the per-tensor cutlass path we run today **can lose LB
score with a strictly better brain**. This is the same failure shape as the 72B-AWQ lane, which died
on decode bandwidth (26–33 actions/window against a ≥100 bar), not on intelligence.

**Format-matched alternative:** `huginnfork/Qwen3.8-27B-FP8` is `compressed-tensors` W8A8
(channel-wise weights, dynamic per-token activations) — the standard, well-trodden
`CompressedTensorsW8A8Fp8` path, much closer to what we validate today and side-stepping block-FP8
entirely. It is 38.49 GB. It is also an **anonymous re-upload made 1 h 04 m after release with 475
downloads**, which is exactly the provenance the sweep flagged as risk #5.

**Secondary, minor:** the official 3.8 repo has an unusual on-disk layout —
`layers-0..63.safetensors` + `outside.safetensors` (6.01 GB) + `mtp.safetensors` instead of the
conventional `model-000NN-of-000NN` sharding, and our current artifact is a *single* 35.92 GB
`model.safetensors`. A `model.safetensors.index.json` is present, so the loader has a map; this is
noted as a staging/attach detail, not a predicted failure.

**⇒ Q3: the wheelhouse is NOT the blocker. "0.19 can't serve the arch" is REFUTED. But "zero code
change" is still false — the change is a quantization-backend change on an SM120 path with one
backend provably off and one NOT ESTABLISHED.**

## §4 — Q4: would it even help?

### 4.1 It does not touch the diagnosed bottleneck

The root cause on record (`learnings/daily_brief_2026-08-12.md:226–233`): the agent re-explores
**because it has forgotten**. At action 129 of a 225-action level spanning 62 analysis steps, the
transcript shows `context_budget_tokens: 31744`, `history_messages: 33`, and reasoning that recalls
*"I already tried clicking on the charcoal and magenta blocks"* **from compacted prose rather than
ground truth**. The harness "already exposes `history`, `transitions` and `last_transition` as
preloaded Python globals; **the agent simply never queries them**." Corroborated independently at
`learnings/daily_brief_2026-08-14.md:115–117`: **66% of turns emit no world-model update at all**,
over 596 archived event files / 50,140 model responses.

A checkpoint swap changes the weights behind the completion endpoint. It does not:

- make the agent reference a Python global its prompt never mentions;
- change `context_budget_tokens`;
- change the 66% no-update rate, which is a scaffold property.

### 4.2 The "262K context" selling point is not new and is not what binds us

`max_position_embeddings` is **262144 in both** 3.6 and 3.8 — the diff in §3.3 returns zero
differing `text_config` keys, and this is one of them. Our stack runs `max-model-len 65536` with an
**analyzer context of 32768** and a 31,744-token budget (`learnings/panel_research_winners.md:7`;
`learnings/a17_v6_diagnosis_2026-07-29.md:103`, which explicitly cleared context-limit as a cause —
"No context/length errors in vLLM log"). **The 31,744 figure is our own configuration, not the
model's ceiling.** A model advertising a longer context cannot relieve a budget we impose ourselves.

### 4.3 On modality — "zero code change" is TRUE on this axis

The task asked whether a VLM arch implies a different input-modality path. It does not, **because we
are already on it**: both checkpoints are `Qwen3_5ForConditionalGeneration` with a `vision_config`;
our served model is tagged `image-text-to-text` / `vlm` on its own card; the harness already runs
`MULTIMODAL_CONTEXT=current_grid`, and the LoRA serve canary already round-trips a real PNG through
this server (`ITERATION_LOG.md:863`). **No modality change. The sweep's framing of this as the #1
failure risk was based on a false premise about what we currently serve.**

### 4.4 The honest case *for* it

Not zero. Our own 08-12 refutation (`learnings/daily_brief_2026-08-12.md:137–138`) concluded the
efficiency ceiling is **≈1.26–1.36 LB — short of gold — and that ~40% of the gap is genuine
capability, not bookkeeping.** A stronger base model is the only lever that attacks that 40%.
So a brain swap is *orthogonal to the #1 bottleneck but aimed at a real, quantified residual.*

What is missing is any measurement of the size of that effect on our stack. The only number in
circulation is one forum claim from a rank-148 competitor ("2x on the local 25 dataset"), with no
artifact, no seeds and no methodology.

## §5 — What this lane would actually cost, stated honestly

The sweep framed this as "a `dataset_sources` swap with zero solver-code change." It is closer to
that than the sweep's own blockers implied — and still not that. The true task list:

1. **Swap the source** — one entry in `DATASET_SOURCES` (notebook cell 6) plus the `MODEL_SLUG`
   resolve (`MODEL_SLUG = 'vrfai-qwen3-6-27b-fp8-hf-snapshot'` → the new slug). **This part genuinely
   is config.** No upload needed — §2.2.
2. **Pick which artifact.** The Kaggle-hosted mirrors are the **official block-FP8** (unvalidated
   GEMM backend on SM120; DeepGEMM provably off). The **format-matched** alternative
   (`huginnfork`, `compressed-tensors`) exists only on **Hugging Face**, so choosing the *safer*
   quantization would require the 38 GB upload the official one lets us skip. **The cheap artifact
   and the safe artifact are not the same artifact.**
3. **A pre-flight file check.** The official FP8 repo ships `preprocessor_config.json` +
   `video_preprocessor_config.json` + `tokenizer_config.json` + `chat_template.jinja`, but **no
   `processor_config.json`** — which our current `vrfai` snapshot *does* have. A missing
   processor-config is the exact defect that would have killed the b122 canary inside
   `get_hf_processor()` **after** paying the full weight-load cost (`ITERATION_LOG.md:845`). The
   split `preprocessor`/`video_preprocessor` pair is probably the modern equivalent and probably
   suffices — **"probably" is NOT ESTABLISHED and this is a free thing to check before a push.**
4. **A boot canary** to answer the one thing source cannot: `ops.cutlass_scaled_mm_supports_block_fp8(120)`,
   plus an aggregate-throughput read at concurrency 28 against the **≥100 actions/window** bar —
   because a slower engine can lose score even with a better brain.

## §7 — VERDICT

# **NOT-WORTH-IT**

*(feasible — more feasible than the sweep believed — but it does not attack the diagnosed bottleneck,
and the evidence that motivated it does not survive contact.)*

**Why not one of the other three.**

- **Not BLOCKED-ON-ARTIFACT.** An official FP8 exists (30.89 GB, 123k downloads) *and* three Kaggle
  FP8 datasets already mirror it in the exact `*-fp8-hf-snapshot` shape our fork consumes. No
  quantization run, no GPU, no upload. `feedback_arc_zero_budget` is not engaged. **§2.**
- **Not BLOCKED-ON-WHEELHOUSE.** vLLM 0.19.0 registers `Qwen3_5ForConditionalGeneration`
  (`registry.py:515`), skips the MTP weights (`qwen3_5.py:700–705`), and upstream's own recipe
  states a **0.17.0+** floor. Decisively: **it is the architecture we already serve** — our current
  `vrfai/Qwen3.6-27B-FP8` declares the identical `architectures`, has a `vision_config`, and is
  tagged `vlm`. The `text_config` diff between the two checkpoints is **empty**. **§3.**
- **Not VIABLE-NOW**, on one clause only: **"genuinely config-only" is NOT ESTABLISHED.** The source
  swap is config, but the *quantization backend* changes — ours is `compressed-tensors` per-tensor
  static; the official 3.8 FP8 is block-FP8 (`weight_block_size [128,128]`, dynamic acts). On SM120
  **DeepGEMM is provably off** (`cuda.py:515–517` + `interface.py:337–349` ⇒ 120//10=12 ≠ 10), and
  CUTLASS block-FP8 support resolves through a **compiled** op that source cannot answer. Worst case
  is the Triton fallback: it runs, but it is the slowest backend — and **action-count efficiency is
  our binding constraint**, so a slower engine can *lose* LB score while reasoning better. Plus the
  missing-`processor_config.json` question (§5 item 3). **§3.4.**

**What actually governs the decision — priority, not feasibility.**

1. **The correlation is UNSUPPORTED (§1).** Zero top-20 entrants have said they used it. The base is
   one rank-148 *local* claim with no LB number and 61 combined downloads across all three Kaggle
   mirrors. The #1 score is timing-**refuted**. This is the exact failure mode
   `feedback_audit_the_instrument` and this campaign's base rate warn about: a tidy story hardening
   faster than its evidence.
2. **It does not touch the root cause (§4).** The agent forgets; the harness exposes `transitions`
   and the agent never queries it; **66% of turns emit no world-model update.** New weights change
   none of that. The "262K context" headline is not even new — both checkpoints declare 262144, and
   our 31,744-token budget is **our own setting**.
3. **The upside is real but unmeasured.** ~40% of the gap to gold is genuine capability
   (`daily_brief_2026-08-12.md:137–138`), and a better brain is the only lever on it. But nobody has
   measured that lever on our stack, and the one public number is a rank-148 local anecdote.

**This is the closest call of the four**, and I want that on the record rather than buried: a
reasonable person could spend one slot on a boot canary here, because the swap turned out to be far
cheaper than the sweep's own blockers implied. I am ruling against it **today** because the case for
spending the slot rested on a correlation that dissolved when I looked at it, and because this week
has already spent ~4 slots and ~3 GPU-h on infra-shaped lanes for **zero capability measurements**.

**Conditions that flip this to a funded screen — pre-registered so it is not re-litigated:**

- **(A) Any named top-20 entrant publicly confirms Qwen3.8** (writeup, public notebook, or an
  unambiguous discussion statement). This is the one that matters; it converts §1 from correlation
  to evidence. Cheap to watch: it costs a discussion sweep we already run daily.
- **(B) A public ARC-AGI-3 notebook attaches any Qwen3.8 artifact** — currently zero (§1.3).
- **(C) The lane can be made free.** The three unknowns (block-FP8 on SM120, processor-config
  sufficiency, throughput vs the ≥100 actions/window bar) are all measurable in a **single** boot
  canary. If it can ride along with a canary already scheduled for another reason, its marginal cost
  is ~0 and it should be taken regardless of (A)/(B).

**Standing correction to carry forward, independent of the verdict:** stop repeating that we "serve
a dense text model" or that a Qwen3.5-family VLM is a new architecture for us. **We have served
`Qwen3_5ForConditionalGeneration`, a vision-language model, for the entire campaign.** That
misconception produced two blockers that were never real, and it will produce more if it survives
this document.
