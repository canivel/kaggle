## 2. Root-cause evidence, ranked by confidence

### PRIMARY (highest confidence) — Model emits tool INTENT as prose, never a parseable tool call; harness re-prompts identically; degenerate repeat loop.

Every response block carries the diagnostic meta:
```
[MODEL RESPONSE META]
finish_reason: stop
tool_call_count: 0
content_chars: 919
reasoning_chars: 0
tool_call_markup_in_text: no
tool_calls_recovered_from_markup: no
```
The assistant text ends with a bare token `python` (narrating that it *will* call the python tool) but emits **no tool-call markup**. Example assistant tail (ft09, repeated verbatim across dozens of turns):
> "Plan: I will now click on the center cell of the third grid (gray center) to see if it causes any changes. This will help me understand the mechanics further and refine the world model.\n**python**"

The harness detects no action, injects the re-prompt:
> "[USER PROMPT] You have not acted yet. Investigate first. ... When calling `python`, emit exactly the tool-call format shown elsewhere ... Do not quote or place tool-call markup inside explanatory text; when you decide to call the tool, emit the tool call itself."

…and the model returns the **byte-identical** 919-char response again (`content_chars: 919` constant). This repeats until the per-turn time budget expires:
```
[ANALYZER STATUS] ... step_executed: False ... message: Yielded control to solver: turn_time_budget.
```
Yield reason is `turn_time_budget.` on essentially every failed turn (ft09 111, lp85 105, sb26 107, vc33 96; plus one `stop_requested.` at end of lp85 and vc33).

**Counts:** 1044/1044 finish_reason=stop; **1044/1044 with tool_call_count matching this pattern except the 8 recovered ones; 0 native tool calls.**

### SECONDARY (high confidence) — The ONLY thing that ever produced an action was the fenced-recovery fallback, and it fired only 8 times.

All 8 executed tool calls have `tool_call_markup_in_text: yes` AND `tool_calls_recovered_from_markup: yes`, with `raw_tool_calls` ids like `"fenced-call-3"`:
```
finish_reason: stop
tool_call_count: 1
tool_call_markup_in_text: yes
tool_calls_recovered_from_markup: yes
raw_tool_calls: [ { "id": "fenced-call-3", ...
```
i.e. on 8 occasions the model happened to emit tool-call-shaped markup *inside its text*, and the fenced-recovery patch salvaged it. The other ~1036 responses had `tool_call_markup_in_text: no` — nothing to recover.

### RULED OUT
- **max_tokens / truncation loop:** `finish_reason: length = 0` across all 1044 responses and 0 occurrences of "length" in the vLLM log. Responses complete cleanly at ~150–920 content chars. **Not the cause.**
- **Request never completing / latency explosion:** vLLM served **1047 requests all HTTP 200**, `Running: 3–4 reqs` and gen throughput 14–93 tok/s continuously for 2.2 h. **Not the cause.**
- **Context-length limit:** No context/length errors in vLLM log; `context_budget_tokens: 31744` (< max_seq_len 32768) held constant on all 113 analyzer-status snapshots per game. The `solver_note "tokens≈75k"` is the **cumulative** generated-token tally over the whole run, not a single prompt — per-turn `history_messages: 24` caps the window. **Not the cause.**
- **Harness deadlock:** the harness was NOT blocked — it actively re-prompted and yielded on `turn_time_budget` every turn; events kept flowing to 13:39–13:40. It is a **livelock (busy repeat loop), not a deadlock.**
- **One client `Read timed out` (read timeout=5.125 s in ft09, 0.976 s in sb26) appears exactly once each** — an incidental late-window blip, not the mechanism (only 1 of 1044 calls affected per game).

## 7. Mechanism summary (worded as measurement)

Generation continued at full health for the entire 2.2-hour window (vLLM served 1047 requests, all HTTP 200, `Running` 3–4 reqs, 14–93 tok/s, `stall_s=0`, MM cache → 100%), but the model's responses show a consistent format defect: on 1044/1044 completions `finish_reason=stop` with **zero native tool calls** (0/1044), and on 1036/1044 the response contained neither a native tool call nor tool-call markup in text — the model narrated its plan and ended with the bare word `python` instead of emitting the tool-call format. The harness detected no action, injected the identical "You have not acted yet" re-prompt, and the model returned the **byte-identical** response (`content_chars` constant per game), producing a livelock that consumed each turn's time budget (`Yielded control to solver: turn_time_budget`) without advancing. The only actions that executed (5, all within the first ~90 s) came exclusively via the fenced-recovery fallback (8 recovered tool calls, ids `fenced-call-N`); native emission never once succeeded. **This failure looks DETERMINISTIC, not stochastic:** the identical-response repetition (same 919-char text re-emitted verbatim under greedy re-prompting), the 0/1044 native-parse rate spread evenly across all four games and both cold and warm cache states, and the format defect being a property of the model×prompt tool-call contract (Qwen2.5-VL-72B-AWQ not emitting this harness's expected native tool-call markup) all indicate it would reproduce on another seed. The seed-2 B2 confirmation run should be expected to reproduce the same near-zero native-parse rate and the same early-freeze-then-livelock signature, barring any change to the tool-call format contract (which is sealed / not permitted).

## Appendix — Taxonomy binning (arXiv 2607.05775 cluster names; feeds NC-4 offline parse study)

The observed failure maps cleanly onto the paper's tool-use failure clusters:

- **C1 "format non-compliance" (primary bin):** 1036/1044 responses (99.2%) — model produces valid natural-language plan but omits the required tool-call schema/markup; `tool_call_markup_in_text: no`. Sub-signature **C1a "narrated-intent / bare-invocation"**: response terminates with the tool name as prose (`python`) rather than an invocation object.
- **C3 "salvageable-markup / recoverable"** : 8/1044 (0.77%) — tool-call-shaped markup present in free text, recovered by fenced parser (`fenced-call-N`). Recovery precision 8/8 = 1.0.
- **C5 "degenerate repetition / prompt-invariant loop"** : the dominant temporal pattern — identical response re-emitted under corrective re-prompt; drives the wall-clock burn. This is the *loop* super-signature that C1 collapses into once re-prompting is added.
- **NOT observed:** C2 "length-truncation" (0), C4 "hallucinated-arguments" (n/a — no calls to inspect), C6 "context-overflow / refusal" (0).

Clean two-cluster fit: **C1 (format non-compliance) → C5 (repetition loop)**, with C3 as the thin recovery channel. Native-emission rate 0.000 is the headline NC-4 datum.
